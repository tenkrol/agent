# Агент-исполнитель (@Tenkrol_ag_bot)

Telegram-агент, который живёт на отдельном сервере (Финляндия, `185.106.94.155`),
принимает задачи в чате и **делает их**: работает с файлами, кодом и документами,
отдаёт результат текстом и файлами, ведёт журнал и учёт расхода — и с недавнего времени
сам следит за хостом.

Движок исполнения — DSH в headless-режиме (модель DeepSeek), каждая задача идёт в
изолированной cgroup с лимитами RAM/CPU/PIDs. Всё, что описано ниже, задеплоено и
проверено живьём (490 тестов).

Итого: агент полностью делает повседневные задачи (файлы, документы, код, ответы), сам
отчитывается о завершённых, следит за хостом и умеет включать алерты — ждём только
наблюдений, чтобы пороги этапа 1 опирались на норму, а не на догадку.

## Что умеет

- **Задачи из Telegram**: текст, фото и сканы (vision + локальный OCR), голосовые
  (SpeechKit STT), документы; многошаговое выполнение с отчётом о шагах.
- **Результат как файл**: DOCX, XLSX, PPTX, PDF, картинки, архивы; LibreOffice и
  Python-окружение стоят на сервере. Файлы уходят в чат и дублируются в архив на
  Яндекс.Диске.
- **Диалог с задачей**: агент может задать уточняющий вопрос (`ВОПРОС:`) или предложить
  варианты (`ВАРИАНТ N:`) — варианты приходят inline-кнопками, ответ продолжает ту же сессию.
- **Голос**: голосовое расшифровывается в задачу, ответ на голосовое приходит текстом и
  голосом (Yandex SpeechKit, тот же ключ, что у чат-бота в Испании).
- **Расписания**: cron-выражения с часовым поясом владельца, `/schedule add|on|off|run|del`.
- **Мост из чат-бота (Испания)**: чат-бот передаёт сложные задачи агенту по SSH-туннелю
  (HTTP на loopback, bearer-токен). Telegram для этого не годится: бот не видит сообщений
  другого бота — проверено и задокументировано.
- **Быстрый слой**: короткий вопрос без файлов и интернета отвечает сама модель за один
  вызов — 212 токенов и 1 секунда против 7 300 токенов и 4,5 секунд у полного запуска.
- **Режим плана**: на большую задачу агент сначала показывает план и ждёт кнопку «Выполнять»;
  для задач без собеседника (мост, расписания) план подмешивается молча, без утверждения.
- **Память**: агент сам ведёт список долговечных фактов о владельце и его делах
  (`/memory`, `/remember`, `/forget`).
- **Автономия (этапы 0–1)**: наблюдатель собирает метрики хоста без модели и считает
  базовую линию (`/observe`); алерты сами просыпаются по триггерам, дедуплицируются,
  молчат в тихие часы и присылают дневную сводку (`/alerts`, `/stop`, `/resume`).
- **Одно сообщение на задачу** (`REPORT_STYLE=brief`, по умолчанию): никаких
  «приступаю», правок прогресса и «выполнена» — только итог: ответ, стоимость и шаги,
  проблемы вложений, пути в архиве на Диске. Файлы, вопрос-уточнение, варианты, план и
  сообщения об ошибках приходят как раньше: они требуют ответа. Прежнее поведение со
  статусами возвращается одной строкой `REPORT_STYLE=verbose`.
- **Отчёт о завершённых задачах**: сторож (`deploy/agent-run-watch`) читает журнал
  сервиса раз в минуту и сообщает владельцу о завершённых и сорванных задачах — и через
  бота-ассистента, и от самого `@Tenkrol_ag_bot` (отметка времени и `flock` не дают
  отчитаться дважды об одной задаче).
- **Связь агент → бот**: задача внутри песочницы может отправить сообщение владельцу
  через `deploy/agent-notify` — он ходит на точку приёма бота по туннелю (`setup-outbox.sh`,
  локальный порт, токен в `/etc/tg-agent/outbox-token`). Ненулевой код возврата означает,
  что сообщение не доставлено, и агент обязан сказать об этом, а не считать задачу
  отчитавшейся.
- **Защита от расхода**: дневной лимит токенов, бюджет на задачу, предел шагов, сброс
  слишком большой беседы, пошаговый лог расхода и оценка в деньгах (`/usage`).

## Как это устроено

```
Telegram ──polling──▶ bot.mjs ──▶ inbox/ (вложения: vision, OCR, STT)
                        │
                        ├── быстрый слой (1 вызов модели) ──▶ ответ сразу
                        ├── режим плана ──▶ утверждение кнопкой
                        └── очередь (до 3) ──▶ DSH в своей cgroup ──▶ outbox/
                        │                                              │
                        ▼                                              ▼
              журнал, расход, алерты, память              файлы в чат + Яндекс.Диск
```

Ключевые узлы:

| Узел | Файл | Ответственность |
|---|---|---|
| Бот | `src/bot.mjs` | приём, доступ, команды, очередь, диалог, отчёты |
| Исполнение | `src/dsh-task.mjs` | запуск DSH, разбор потока событий, таймаут, лимиты, cgroup |
| Изоляция | `src/cgroup.mjs` | лимиты RAM/CPU/PIDs на каждую задачу |
| Вход | `src/inbox.mjs`, `src/vision.mjs`, `src/ocr.mjs`, `src/stt.mjs` | фото, сканы, голос → текст |
| Диалог | `src/reply-protocol.mjs` | `ВОПРОС:`, `ВАРИАНТ N:`, продолжение сессии |
| Учёт | `src/usage.mjs`, `src/pricing.mjs`, `src/tasks.mjs` | токены, деньги, журнал задач |
| Планировщик | `src/schedule.mjs` | cron, повторные задачи, догон пропущенных |
| Мост | `src/bridge-http.mjs` | приём задач от чат-бота по туннелю |
| Диск | `src/yandex-disk.mjs` | архив результатов, публичные ссылки, выгрузка |
| Наблюдатель | `src/observe.mjs`, `deploy/metrics-collect.sh` | метрики, базовая линия, готовность, пороги |
| Алерты | `src/alerts.mjs`, `src/alerts-cli.mjs`, `src/notify.mjs` | триггеры, дедуп, тихие часы, сводка |
| Память | `src/memory.mjs` | долговечные факты о владельце |
| Отчёты владельцу | `deploy/agent-run-watch`, `deploy/agent-notify` | сторож завершённых задач, связь из песочницы через туннель |

Состояние живёт в `/var/lib/agent/state` (журнал задач, расход, память, наблюдения,
алерты) и каждый день бэкапится — локально и копией на Яндекс.Диск.

## Связь с чат-ботом и отчёты

Задача исполняется в песочнице и не может сама обратиться к Telegram агента, поэтому
связь устроена через второй контур:

- `deploy/setup-outbox.sh` поднимает туннель к точке приёма бота-ассистента и кладёт токен
  в `/etc/tg-agent/outbox-token` (600);
- `deploy/agent-notify "текст"` — команда, которой задача сообщает владельцу о результате
  (код возврата ≠ 0 значит «не доставлено», и об этом нужно сказать);
- `deploy/agent-run-watch` — сторож: раз в минуту смотрит журнал `dsh-agent` и отчитывается
  о завершённых и сорванных задачах двумя путями (ассистент и сам агент), защищаясь от
  повторных отчётов отметкой времени и `flock`.

## Расход и защита

Расход растёт как **шаги × контекст**: каждый шаг отправляет модели всю историю задачи.
Замеры 8–12 октября: 14 запусков, 4,65 млн токенов, $0,112 — при этом три задачи дали 67%
расхода, а задачи с 11+ шагами — 78%.

| Мера | Настройка |
|---|---|
| Дневной лимит | `DAILY_TOKEN_LIMIT=3000000` |
| Потолок на задачу | `TASK_TOKEN_BUDGET=1500000`, предупреждение с 300 000 |
| Предел шагов | `TASK_MAX_STEPS=16` (рекорд был 28 шагов и 1,42 млн токенов) |
| Сброс большой беседы | `SESSION_MAX_TOKENS=60000` |
| Быстрый слой | короткие вопросы без DSH: 35× дешевле, 5× быстрее |
| Автономные задачи | свежая сессия и тихий план — не платят за историю беседы |
| Сбор метрик и алерты | без модели: **0 токенов** |

Важно про цифры: 95–96% токенов — попадания в кэш, они в 50 раз дешевле нового входа,
поэтому «миллион токенов» и «миллион токенов по цене» — разные вещи. Кэш виден в `/usage`.

## Установка и эксплуатация

```bash
# деплой с локальной машины (архив без .git и .env)
COPYFILE_DISABLE=1 tar czf /tmp/agent-deploy.tgz \
  --exclude='.git' --exclude='.env' --exclude='node_modules' --exclude='.DS_Store' agent
scp -i <ключ> /tmp/agent-deploy.tgz root@185.106.94.155:/tmp/
ssh -i <ключ> root@185.106.94.155 \
  'rm -rf /tmp/agent-deploy && mkdir -p /tmp/agent-deploy && \
   tar xzf /tmp/agent-deploy.tgz -C /tmp/agent-deploy && \
   cd /tmp/agent-deploy/agent && bash deploy/install-remote.sh'
```

Установщик раскладывает релиз в `/opt/agent-releases` и переключает симлинк `/opt/agent`,
ставит юниты (`dsh-agent`, `agent-backup`, `agent-metrics`, `agent-alerts`), **никогда не
перезаписывает** `/etc/agent/agent.env` (сначала бэкап, потом догоняет отсутствующие
переменные) и печатает состояние. Секреты меняются отдельно:

```bash
bash deploy/rotate-from-mac.sh --api-key      # новый ключ модели, с проверкой и откатом
bash deploy/set-env.sh KEY=VALUE              # точечная правка окружения
printf '%s' "$SECRET" | bash deploy/set-env.sh --stdin KEY   # секрет через stdin
```

Диагностика:

```bash
systemctl list-timers agent-metrics.timer agent-alerts.timer agent-backup.timer
tail -1 /var/lib/agent/state/observations.jsonl
tail -1 /var/lib/agent/state/alerts.jsonl
journalctl -u dsh-agent -f
```

## Тесты и разработка

```bash
node --test test/*.test.mjs      # 490 тестов, фикстуры лежат в fixtures/
```

E5 implementation check — контрольная строка README для заявки REQ-0009 (change PLA-32);
её наличие проверяет `test/readme.test.mjs`.

Правила, которые стоит помнить при правках: задача всегда идёт в cgroup с лимитами;
`MemoryDenyWriteExecute` включать нельзя (V8 падает); `ProtectControlGroups=false`
обязателен для делегирования cgroup; секреты не попадают в задачи; журнал алертов —
append-only, его нельзя компактить как журнал задач.

## Ограничения и открытые решения

- **Длинные записи** (больше ~30 секунд) не распознаются: ограничение SpeechKit v1 —
  запись честно помечается как нераспознанная.
- **Испания**: доступ к её метрикам не настроен (мост односторонний, Испания → Финляндия),
  поэтому «присмотр за ботами tg/vk» пока вне объёма. Параллельная сессия подготовила
  *описание* такого наблюдателя (`README_harness_etap0.md`: read-only харнесс на испанском
  хосте со своим `harness.yaml`, `heartbeat.sh` и журналом) — но самих файлов и развёртывания
  нет ни локально, ни на сервере: на Испании каталога `~/agent-harness` и юнитов не найдено.
  Прежде чем делать второй наблюдатель, стоит решить, чей он: мой `src/observe.mjs` уже
  собирает метрики финского хоста, испанский харнесс дополнил бы картину, а не заменил её.
- **Права для этапа 3**: агент работает без root (`ProtectSystem=strict`, запись только в
  `/var/lib/agent`); для действий нужна узкая политика sudoers или root-хелпер с
  валидированным интерфейсом — решение не принято.
- **Компакция DSH**: настройки профиля проверены A/B и эффекта не дают (в headless
  автосжатие не срабатывает), поэтому контекст ограничивается на стороне бота.


## Заявки и доработки: как пользоваться

С E3–E7 доработка проходит путь **заявка → компонентные спеки → реализация → проверки
→ установка**. Всё, кроме установки, автоматизировано; установку запускает владелец/root.

### 1. Создать заявку

В чате бота (Испания):

```
/request добавь в бота команду показа релиза агента
```

Бот вернёт `requestId`, компоненты, вопрос (если формулировка неоднозначна) и ссылку.
Или напрямую, с сервера агента:

```sh
TOKEN=$(grep '^BRIDGE_TOKEN=' /etc/agent/agent.env | cut -d= -f2-)
curl -sS -X POST http://127.0.0.1:8787/v1/requests   -H "authorization: Bearer $TOKEN" -H 'content-type: application/json'   -d '{"text":"Бот должен показывать релиз агента","title":"Версия агента"}'
```

Агент создаёт draft в `tenkrol/assistant-work`, определяет компоненты
(`tenkrol/agent`/`tenkrol/assistant`), генерирует `proposal/design/tasks/acceptance`,
выделяет `changeId` и публикует:

- `req/<REQ>` — заявка и `manifest.json`;
- `spec/<REQ>-<changeId>` — компонентные OpenSpec-ветки;
- в manifest — `baseCommit` и `specificationCommit`.

### 2. Реализовать

```sh
curl -sS -X POST http://127.0.0.1:8787/v1/implement   -H "authorization: Bearer $TOKEN" -H 'content-type: application/json'   -d '{"requestId":"REQ-0009"}'
```

DSH работает в отдельном checkout компонента, затем:

1. запускаются тесты и `spec-check`;
2. при падении — repair с выводом ошибок (до 2 попыток);
3. только после зелёных проверок пушится `impl/<REQ>-<changeId>`.

### 3. Установить

```sh
curl -sS -X POST http://127.0.0.1:8787/v1/deploy   -H "authorization: Bearer $TOKEN" -H 'content-type: application/json'   -d '{"requestId":"REQ-0009","confirm":"REQ-0009","component":"tenkrol/agent","branch":"impl/REQ-0009-PLA-32"}'
```

Нужно точное подтверждение (`confirm == requestId`). Сервис повторно проверяет ветку,
делает merge в main и возвращает шаг установки. Установку выполняет владелец:

```sh
cd /tmp/agent-deploy/tenkrol-agent && sudo bash deploy/install-remote.sh
```

### 4. Наблюдение

```sh
curl -sS -H "authorization: Bearer $TOKEN" http://127.0.0.1:8787/v1/agents
curl -sS -H "authorization: Bearer $TOKEN" "http://127.0.0.1:8787/v1/activity?limit=10"
curl -sS -H "authorization: Bearer $TOKEN" http://127.0.0.1:8787/v1/usage
```

`/v1/agents` — реестр и профили моделей, `/v1/activity` — события задач,
`/v1/usage` — расход. Пример ответа `/v1/requests` содержит `analysis.specs` и
`analysis.attachments` с changeId/SHA.

### Ограничения

- PR через GitHub API не создаются: deploy key умеет clone/push; используйте compare URL
  или добавьте fine-grained token/App.
- Установка требует root: процесс агента работает под `agent` без sudo.
- Параллельность — только с `WORKSPACE_PER_TASK=true`; иначе задачи делят workspace.
