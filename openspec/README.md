# Как работаем (ритуал OpenSpec)

## Кто что делает
- **Владелец:** описывает задачу словами, читает спеку, одобряет или правит.
- **Агент (сессия):** пишет proposal, дельту-спеку, design и tasks; после одобрения
  реализует, тестирует, деплоит, обновляет handoff и архивирует изменение.
- Любая другая сессия читает `AGENTS.md` в корне и продолжает по тем же правилам.

## Шаги
1. **Задача словами** — «хочу, чтобы …».
2. **Спека.** Папка `changes/PLA-<номер>/` (номер сквозной по порядку): `proposal.md` (зачем и что),
   `specs/<домен>/spec.md` (требования «ДОЛЖЕН» + сценарии GIVEN/WHEN/THEN),
   `design.md` (как), `tasks.md` (чек-лист). Владелец одобряет.
3. **Реализация** по `tasks.md`, с тестами. Если спека оказалась неверной — правим спеку,
   а не молча код.
4. **Проверка** — локальный прогон тестов → `deploy/install-remote.sh` → проверка живого
   поведения.
5. **Архив** — дельта вливается в `openspec/specs/`, папка уезжает в
   `changes/archive/PLA-<номер>/`, `HANDOFF.md` обновляется, коммит.

## Номер изменения
Папки называются `PLA-<номер>`, номер сквозной. Новый номер — последний в `changes/archive/`
или среди активных изменений, плюс один (на 2026-10-17 следующий свободный — `PLA-18`).
Карта «номер → что это» — `changes/archive/README.md`.

## Статусы
`changes/<папка>/` — в работе; `changes/archive/` — завершено. Если раздел спеки не
описан — писать «не знаю», а не оставлять пустым.

## Проверка
```sh
bash tools/spec-check.sh          # структура changes и дельт
node --test --test-force-exit test/*.test.mjs
```
