# Спека домена config

## ADDED Requirements

### Requirement: Единственный источник настроек
Окружение ДОЛЖНО читаться только внутри домена `config`. Остальные домены получают
готовый объект настроек и не читают конкретные ключи `process.env`. Допустимое
исключение — передача окружения дочернему процессу целиком (`env = process.env` при
запуске DSH): это не чтение настроек, а среда исполнения.

#### Scenario: Новый домен просит настройку
- GIVEN домену нужен новый параметр
- WHEN он добавляется
- THEN поле появляется в `config` с валидацией и значением по умолчанию
- AND домен импортирует только публичный API

#### Scenario: Чтение env в обход config
- GIVEN в `src/` (вне `src/config/`) появляется `process.env`
- WHEN запускается сторожевой тест
- THEN тест падает и указывает файл
- AND правка переносится в `config`

### Requirement: Валидация при старте
Неверное значение переменной ДОЛЖНО давать понятную ошибку сразу при старте, с именем
переменной и допустимыми границами, а не падать в середине работы.

#### Scenario: Отрицательный лимит
- GIVEN `DAILY_TOKEN_LIMIT=-5`
- WHEN сервис запускается
- THEN старт прерывается ошибкой `DAILY_TOKEN_LIMIT: …`
- AND сообщение не раскрывает значения секретов

### Requirement: Настройки связи с ботом живут в конфиге
Параметры точки приёма ответов чат-бота (`OUTBOX_URL` и токен) ДОЛЖНЫ читаться доменом
`config` (секция `outbox`), а не напрямую из окружения в модуле отправки. Токен ДОЛЖЕН
попадать в список секретов, чтобы не печататься в логах.

#### Scenario: Ответ дублируется в бота
- GIVEN агенту нужно продублировать ответ в чат-бота
- WHEN модуль отправки берёт настройки
- THEN адрес и токен приходят из `config.outbox`
- AND сторожевой тест не находит чтения `process.env` в модуле отправки

#### Scenario: Токен в логах
- GIVEN конфиг печатается при диагностике
- WHEN выводится список секретов
- THEN значение токена `OUTBOX_TOKEN` маскируется

### Requirement: Набор переменных и умолчаний не меняется
Перенос ДОЛЖЕН сохранять все существующие переменные, их значения по умолчанию, границы
и форматы (время `ЧЧ:ММ`, список пользователей, абсолютные пути). Новые переменные
добавляются только вместе с документированным значением по умолчанию и не меняют смысл
прежних.

В этом изменении добавляются: `RECOVERY_NOTIFY` (true) — сообщать о восстановлении задач
после перезапуска; `ACTION_LOG` (true) — вести журнал внешних действий; `ACTION_LOG_MAX`
(5000) — предел записей журнала действий перед компакцией.

#### Scenario: Совместимость
- GIVEN старый `/etc/agent/agent.env`
- WHEN сервис стартует после обновления
- THEN конфиг собирается без ошибок
- AND поведение агента при нормальной работе не меняется

#### Scenario: Новые настройки
- GIVEN в окружении нет новых ключей
- WHEN конфиг загружается
- THEN `RECOVERY_NOTIFY`, `ACTION_LOG` и `ACTION_LOG_MAX` получают значения по умолчанию
- AND неверное значение даёт понятную ошибку старта

## ADDED Requirements

### Requirement: Настройки проверки результата
Домен `config` ДОЛЖЕН читать, валидировать и отдавать остальным доменам настройки проверки
результата (PLA-15), с значениями по умолчанию и понятной ошибкой при старте:

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `VERIFY` | `true` | включить проверку результата |
| `VERIFY_MAX_ATTEMPTS` | `1` | сколько повторных попыток исправления после провала проверки |
| `VERIFY_TIMEOUT_MS` | `300000` | предел времени одной проверки |
| `VERIFY_RENDER` | `true` | рендер документа при значимых требованиях к оформлению |
| `VERIFY_MODEL_MAX_CHARS` | `12000` | предел текста, передаваемого модельной проверке |
| `VERIFY_CHECK_ALLOWLIST` | типовые команды проверок | список разрешённых argv-команд проверок кода |

Требования к значениям:
- `VERIFY` и `VERIFY_RENDER` — булевы (`true/false/1/0/yes/no`);
- `VERIFY_MAX_ATTEMPTS` — целое от 0 до 5; `VERIFY_TIMEOUT_MS` — целое от 10 000 до
  1 800 000; `VERIFY_MODEL_MAX_CHARS` — целое от 1 000 до 200 000;
- `VERIFY_CHECK_ALLOWLIST` — список argv-команд, разделённых `;`; каждая команда
  разбирается на аргументы без оболочки, пустые элементы отбрасываются; пустое значение
  допустимо и означает «проверки кода недоступны»;
- неверное значение ДОЛЖНО давать `ConfigError` при старте с именем переменной и границами,
  не раскрывая секретов;
- `VERIFY=false` — допустимое значение (осознанный выключатель), а не ошибка.

#### Scenario: Значения по умолчанию
- GIVEN переменные проверки не заданы
- WHEN сервис запускается
- THEN включаются значения по умолчанию из таблицы
- AND агент работает с проверкой результата

#### Scenario: Неверный лимит
- GIVEN `VERIFY_MAX_ATTEMPTS=-1`
- WHEN сервис запускается
- THEN старт прерывается ошибкой `VERIFY_MAX_ATTEMPTS: …`
- AND сообщение не содержит значений секретов

#### Scenario: Allowlist команд
- GIVEN `VERIFY_CHECK_ALLOWLIST="node --test;npm test"`
- WHEN конфиг собирается
- THEN домен получает две argv-команды
- AND оболочка не используется при их запуске

#### Scenario: Пустой allowlist
- GIVEN `VERIFY_CHECK_ALLOWLIST=""`
- WHEN конфиг собирается
- THEN значение считается заданным и пустым
- AND проверки кода трактуются как недоступные, а не «разрешено всё»

#### Scenario: Проверка выключена
- GIVEN `VERIFY=false`
- WHEN сервис запускается
- THEN конфиг валиден
- AND проверка отключается с явной пометкой в отчёте

### Requirement: Настройки проверки не дублируются
Ключи проверки ДОЛЖНЫ читаться только в `config`; `verification`, `execution`, `tools` и
`delivery` получают готовые значения и НЕ ДОЛЖНЫ читать `process.env` или собственные
переменные окружения для этих настроек.

#### Scenario: Чтение в обход
- GIVEN в `src/verification/` появляется чтение `process.env.VERIFY`
- WHEN запускается сторожевой тест
- THEN тест падает и указывает файл
- AND значение переносится в `config`
