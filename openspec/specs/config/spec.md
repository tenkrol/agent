# Спека домена config

## ADDED Requirements

### Requirement: Единственный источник настроек
Окружение ДОЛЖНО читаться только внутри домена `config`. Остальные домены получают
готовый объект настроек и не читают конкретные ключи `process.env`. Допустимое
исключение — передача окружения дочернему процессу целиком (`env = process.env` при
запуске DSH): это не чтение настроек, а среда исполнения.

#### Scenario: Новый домен просит настройку
- GIVEN домену нужен новый параметр
- WHEN он добавляется
- THEN поле появляется в `config` с валидацией и значением по умолчанию
- AND домен импортирует только публичный API

#### Scenario: Чтение env в обход config
- GIVEN в `src/` (вне `src/config/`) появляется `process.env`
- WHEN запускается сторожевой тест
- THEN тест падает и указывает файл
- AND правка переносится в `config`

### Requirement: Валидация при старте
Неверное значение переменной ДОЛЖНО давать понятную ошибку сразу при старте, с именем
переменной и допустимыми границами, а не падать в середине работы.

#### Scenario: Отрицательный лимит
- GIVEN `DAILY_TOKEN_LIMIT=-5`
- WHEN сервис запускается
- THEN старт прерывается ошибкой `DAILY_TOKEN_LIMIT: …`
- AND сообщение не раскрывает значения секретов

### Requirement: Настройки связи с ботом живут в конфиге
Параметры точки приёма ответов чат-бота (`OUTBOX_URL` и токен) ДОЛЖНЫ читаться доменом
`config` (секция `outbox`), а не напрямую из окружения в модуле отправки. Токен ДОЛЖЕН
попадать в список секретов, чтобы не печататься в логах.

#### Scenario: Ответ дублируется в бота
- GIVEN агенту нужно продублировать ответ в чат-бота
- WHEN модуль отправки берёт настройки
- THEN адрес и токен приходят из `config.outbox`
- AND сторожевой тест не находит чтения `process.env` в модуле отправки

#### Scenario: Токен в логах
- GIVEN конфиг печатается при диагностике
- WHEN выводится список секретов
- THEN значение токена `OUTBOX_TOKEN` маскируется

### Requirement: Набор переменных и умолчаний не меняется
Перенос ДОЛЖЕН сохранить все существующие переменные, их значения по умолчанию, границы
и форматы (время `ЧЧ:ММ`, список пользователей, абсолютные пути). Новые переменные памяти
ДОБАВЛЯЮТСЯ с умолчаниями из требования «Настройки памяти»; существующие ключи и их
поведение не меняются.

#### Scenario: Совместимость
- GIVEN старый `/etc/agent/agent.env`
- WHEN сервис стартует после переноса
- THEN конфиг собирается без ошибок
- AND поведение агента не меняется, новые ключи берут умолчания

## ADDED Requirements

### Requirement: Настройки проверки результата
Домен `config` ДОЛЖЕН читать, валидировать и отдавать остальным доменам настройки проверки
результата (PLA-15), с значениями по умолчанию и понятной ошибкой при старте:

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `VERIFY` | `true` | включить проверку результата |
| `VERIFY_MAX_ATTEMPTS` | `1` | сколько повторных попыток исправления после провала проверки |
| `VERIFY_TIMEOUT_MS` | `300000` | предел времени одной проверки |
| `VERIFY_RENDER` | `true` | рендер документа при значимых требованиях к оформлению |
| `VERIFY_MODEL_MAX_CHARS` | `12000` | предел текста, передаваемого модельной проверке |
| `VERIFY_CHECK_ALLOWLIST` | типовые команды проверок | список разрешённых argv-команд проверок кода |

Требования к значениям:
- `VERIFY` и `VERIFY_RENDER` — булевы (`true/false/1/0/yes/no`);
- `VERIFY_MAX_ATTEMPTS` — целое от 0 до 5; `VERIFY_TIMEOUT_MS` — целое от 10 000 до
  1 800 000; `VERIFY_MODEL_MAX_CHARS` — целое от 1 000 до 200 000;
- `VERIFY_CHECK_ALLOWLIST` — список argv-команд, разделённых `;`; каждая команда
  разбирается на аргументы без оболочки, пустые элементы отбрасываются; пустое значение
  допустимо и означает «проверки кода недоступны»;
- неверное значение ДОЛЖНО давать `ConfigError` при старте с именем переменной и границами,
  не раскрывая секретов;
- `VERIFY=false` — допустимое значение (осознанный выключатель), а не ошибка.

#### Scenario: Значения по умолчанию
- GIVEN переменные проверки не заданы
- WHEN сервис запускается
- THEN включаются значения по умолчанию из таблицы
- AND агент работает с проверкой результата

#### Scenario: Неверный лимит
- GIVEN `VERIFY_MAX_ATTEMPTS=-1`
- WHEN сервис запускается
- THEN старт прерывается ошибкой `VERIFY_MAX_ATTEMPTS: …`
- AND сообщение не содержит значений секретов

#### Scenario: Allowlist команд
- GIVEN `VERIFY_CHECK_ALLOWLIST="node --test;npm test"`
- WHEN конфиг собирается
- THEN домен получает две argv-команды
- AND оболочка не используется при их запуске

#### Scenario: Пустой allowlist
- GIVEN `VERIFY_CHECK_ALLOWLIST=""`
- WHEN конфиг собирается
- THEN значение считается заданным и пустым
- AND проверки кода трактуются как недоступные, а не «разрешено всё»

#### Scenario: Проверка выключена
- GIVEN `VERIFY=false`
- WHEN сервис запускается
- THEN конфиг валиден
- AND проверка отключается с явной пометкой в отчёте

### Requirement: Настройки проверки не дублируются
Ключи проверки ДОЛЖНЫ читаться только в `config`; `verification`, `execution`, `tools` и
`delivery` получают готовые значения и НЕ ДОЛЖНЫ читать `process.env` или собственные
переменные окружения для этих настроек.

#### Scenario: Чтение в обход
- GIVEN в `src/verification/` появляется чтение `process.env.VERIFY`
- WHEN запускается сторожевой тест
- THEN тест падает и указывает файл
- AND значение переносится в `config`

## ADDED Requirements

### Requirement: Настройки контракта v2 и доставки
Домен `config` ДОЛЖЕН содержать настройки контракта v2, файлов и доставки, отдавать их
остальным доменам готовыми значениями и не требовать чтения `process.env` вне `config`.

| Ключ | Значение по умолчанию | Валидация |
|---|---|---|
| `CONTRACT_V2` | `true` | true/false |
| `BRIDGE_ROUTE_BOT_ID` | пусто | строка; пусто — маршрут не ограничен по боту |
| `BRIDGE_ROUTE_CHAT_ID` | пусто | строка; пусто — маршрут не ограничен по чату |
| `DELIVERY_TICK_MS` | `30000` | целое 1000…600000 |
| `DELIVERY_RETRY_MS` | `60000,300000,900000,3600000,21600000` | список целых ≥ 1000 |
| `DELIVERY_MAX_ATTEMPTS` | `8` | целое 1…50 |
| `DELIVERY_TEXT_CHARS` | `3500` | целое 500…4096 |
| `FILES_MAX_BYTES` | `20971520` | целое 1024…104857600 |

#### Scenario: Значения по умолчанию
- GIVEN новые ключи не заданы
- WHEN сервис стартует
- THEN `CONTRACT_V2=true`, доставка работает с тиком 30 с и восемью попытками
- AND текст ассистенту обрезается до 3 500 символов

#### Scenario: Отключение контракта v2
- GIVEN `CONTRACT_V2=false`
- WHEN сервис стартует
- THEN `/v1/*` не включается, работают прежние `/bridge` и `/outbox`
- AND остальные настройки не меняются

#### Scenario: Ограничение маршрута
- GIVEN заданы `BRIDGE_ROUTE_BOT_ID` и `BRIDGE_ROUTE_CHAT_ID`
- WHEN приходит задача с чужим маршрутом
- THEN домен `bot-link` отклоняет запрос
- AND значения маршрута берутся из `config`, а не из окружения напрямую

#### Scenario: Неверный список повторов
- GIVEN `DELIVERY_RETRY_MS` содержит нечисло
- WHEN конфиг собирается
- THEN старт прерывается ошибкой `DELIVERY_RETRY_MS: …`
- AND понятно, что нужен список целых миллисекунд

#### Scenario: Секреты не раскрываются
- GIVEN в настройках есть токены
- WHEN конфиг печатается при диагностике
- THEN значения токенов маскируются
- AND новые ключи не добавляют секретов в открытом виде

## ADDED Requirements

### Requirement: Настройки процедур
Домен `config` ДОЛЖЕН читать, валидировать и отдавать домену `procedures` настройки
хранения версий, с значениями по умолчанию и понятной ошибкой при старте:

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `PROCEDURES_MAX_VERSIONS` | `20` | сколько версий одной процедуры хранится |
| `PROCEDURES_RETENTION_DAYS` | `365` | сколько дней хранятся удалённые процедуры и архивные версии |

Требования к значениям:
- `PROCEDURES_MAX_VERSIONS` — целое от 1 до 200; предел применяется только к архивным
  версиям и не удаляет версии, на которые ссылаются задачи;
- `PROCEDURES_RETENTION_DAYS` — целое от 1 до 3650; значение меньше `OUTPUT_RETENTION_DAYS`
  (срок хранения результатов) НЕ ДОПУСКАЕТСЯ, иначе версия, на которую ссылается задача,
  может исчезнуть раньше результата;
- неверное значение ДОЛЖНО давать `ConfigError` при старте с именем переменной и границами,
  не раскрывая секретов.

#### Scenario: Значения по умолчанию
- GIVEN переменные процедур не заданы
- WHEN сервис запускается
- THEN включаются значения по умолчанию из таблицы
- AND процедуры хранят не больше 20 версий и 365 дней архивных записей

#### Scenario: Неверный предел
- GIVEN `PROCEDURES_MAX_VERSIONS=0`
- WHEN сервис запускается
- THEN старт прерывается ошибкой `PROCEDURES_MAX_VERSIONS: …`
- AND сообщение не содержит значений секретов

#### Scenario: Срок меньше хранения результатов
- GIVEN `PROCEDURES_RETENTION_DAYS` меньше `OUTPUT_RETENTION_DAYS`
- WHEN конфиг собирается
- THEN старт прерывается ошибкой `PROCEDURES_RETENTION_DAYS: …` с объяснением минимума
- AND версии, на которые ссылаются задачи, не могут быть удалены раньше результата

#### Scenario: Предел числа версий и ссылки задач
- GIVEN у процедуры больше архивных версий, чем `PROCEDURES_MAX_VERSIONS`
- WHEN выполняется уборка
- THEN удаляются самые старые архивные версии
- AND версии, на которые ссылаются задачи, сохраняются

### Requirement: Настройки процедур не дублируются
Ключи процедур ДОЛЖНЫ читаться только в `config`; домен `procedures` и `storage` получают
готовые значения и НЕ ДОЛЖНЫ читать `process.env` или собственные переменные окружения для
этих настроек.

#### Scenario: Чтение в обход
- GIVEN в `src/procedures/` появляется чтение `process.env.PROCEDURES_MAX_VERSIONS`
- WHEN запускается сторожевой тест
- THEN тест падает и указывает файл
- AND значение переносится в `config`

## ADDED Requirements

### Requirement: Настройки памяти
Домен `config` ДОЛЖЕН отдавать настройки памяти одной секцией с валидацией и значениями по
умолчанию:

| Ключ | По умолчанию | Границы | Назначение |
|---|---|---|---|
| `MEMORY_CONTEXT_CHARS` | 1500 | 200–8000 | бюджет памяти в промпте |
| `MEMORY_HISTORY_MAX` | 500 | 50–5000 | предел истории (заменённые/истёкшие) |
| `MEMORY_TASK_RETENTION_DAYS` | 7 | 0–365 | срок хранения контекста закрытой задачи |
| `MEMORY_MAX_FACTS` | 120 | 10–1000 | предел активных фактов |
| `MEMORY_SECRET_SCAN` | true | boolean | скан старых фактов при миграции; показ фильтрует всегда |

Ключи ДОЛЖНЫ быть описаны в `config`, `.env.example` и README. Значения секретов в этих
ключах не встречаются; неверное значение ДОЛЖНО давать понятную ошибку при старте с именем
переменной и границами.

#### Scenario: Значения по умолчанию
- GIVEN переменные памяти не заданы
- WHEN конфиг собирается
- THEN действуют значения по умолчанию из таблицы
- AND поведение памяти определено

#### Scenario: Неверное значение
- GIVEN `MEMORY_CONTEXT_CHARS=10`
- WHEN сервис запускается
- THEN старт прерывается ошибкой `MEMORY_CONTEXT_CHARS: …`
- AND сообщение не раскрывает значения секретов

#### Scenario: Выключенный скан
- GIVEN `MEMORY_SECRET_SCAN=false`
- WHEN память загружается и показывается
- THEN скан при миграции не выполняется
- AND фильтрация секретов при записи, показе, промпте и отчёте всё равно работает
