# Спека домена bot-link

## ADDED Requirements

### Requirement: Протокол моста живёт в домене
Приём задач от чат-бота (поля запроса, проверка токена, ограничение длины, ответ) ДОЛЖЕН
быть в домене `bot-link`; формат протокола описан в спеке и контракте
`openspec/specs/bot-link/contract.md` и не прячется в ядре. Контракт версионируется:
версия 2 работает по `/v1/*`, прежний `/bridge` остаётся как совместимый вход. Поле
`context.facts` и событие `memory_proposal` описаны в том же контракте; формат
синхронизирован с изменением PLA-14.

#### Scenario: Задача от бота
- GIVEN чат-бот отправляет задачу по контракту v2
- WHEN домен её принимает
- THEN проверяются токен, версия, маршрут, длина и формат `context.facts`
- AND задача сохраняется и бот получает идентификатор и состояние

#### Scenario: Неверный токен
- GIVEN запрос без верного токена
- WHEN домен обрабатывает его
- THEN ответ 401 и задача не создаётся

#### Scenario: Старый клиент
- GIVEN клиент работает по прежнему `/bridge`
- WHEN он отправляет `task` и `source`
- THEN задача принимается и ответ совместим с прежним
- AND маршрут ответа считается личным чатом агента

### Requirement: Зеркалирование ответа — правило домена
Решение доставлять ответ ассистенту, состав и формат события ДОЛЖНЫ быть в домене;
HTTP-вызов делает интеграционный клиент, а не ядро. Доставка идёт событиями с постоянным
идентификатором и подтверждением обработки. Пользовательские события — только `result` и
`question`; текст результата обрезается до `DELIVERY_TEXT_CHARS` и отправляется с заголовком
«Ответ агента».

#### Scenario: Успешная задача
- GIVEN задача пришла от ассистента и завершилась
- WHEN результат доставляется
- THEN событие `result` содержит `eventId`, маршрут, обрезанный текст с заголовком «Ответ агента» и файлы
- AND ошибка доставки не ломает ответ владельцу

#### Scenario: Очень длинный результат
- GIVEN текст результата больше `DELIVERY_TEXT_CHARS`
- WHEN событие результата собирается
- THEN текст обрезан до предела и помечен
- AND заголовок сообщения — «Ответ агента»

#### Scenario: Токен не настроен
- GIVEN точка приёма не настроена
- WHEN ответ готов
- THEN доставка ассистенту молча пропускается
- AND в чат агента ответ уходит как обычно

### Requirement: Ядро не ходит в сеть
После этого изменения `bot.mjs` НЕ ДОЛЖЕН содержать сетевых вызовов: вход и выход моста
живут в домене, транспорт — в `integrations`.

#### Scenario: Проверка границ
- GIVEN сторожевой тест ищет `fetch(` вне `integrations`
- WHEN проверка проходит по `src/`
- THEN `bot.mjs` не попадает в нарушители

## ADDED Requirements

### Requirement: В чат-бота уходит только результат и запрос информации
Доставка ДОЛЖНА отправлять ассистенту только пользовательские события: финальный результат
задачи и запрос дополнительной информации (уточняющий вопрос или предложенные варианты).
Служебные сообщения — статусы, прогресс, отметки о завершении, сводки, алерты, план на
утверждение — НЕ ДОЛЖНЫ доставляться. Служебные события без сообщения пользователю
(`memory_proposal`) доставляться МОГУТ: они не создают сообщение в разговоре и не имеют
полей пользовательского текста (`text`/`title`); решение принимает ассистент.

#### Scenario: Обычная задача
- GIVEN задача завершилась
- WHEN агент отправляет результат в свой чат
- THEN ассистенту уходит ровно одно пользовательское событие результата
- AND статусы и прогресс не доставляются

#### Scenario: Предложение памяти
- GIVEN агент предлагает сохранить рабочий факт
- WHEN событие `memory_proposal` доходит до ассистента
- THEN оно не создаёт сообщение пользователю
- AND подтверждение обработки приходит как для обычного события

### Requirement: Зеркалирование не влияет на доставку
Ошибка доставки НЕ ДОЛЖНА влиять на отправку в чат агента и на состояние выполнения задачи.

#### Scenario: Точка приёма недоступна
- GIVEN `postAgentEvent` вернул ошибку
- WHEN результат отправлен владельцу в чат агента
- THEN задача остаётся выполненной
- AND доставка повторяется с тем же `eventId`, задача не запускается заново

### Requirement: Подтверждение после сохранения
Приём задачи от ассистента ДОЛЖЕН подтверждаться успешным ответом только после
долговечного сохранения задачи. При ошибке сохранения задача не принимается и выполнение
не начинается.

#### Scenario: Успешный приём
- GIVEN хранилище доступно
- WHEN приходит корректный запрос с задачей
- THEN задача сохраняется
- AND мост получает `202` с идентификатором задачи

#### Scenario: Ошибка сохранения
- GIVEN хранилище недоступно
- WHEN приходит корректный запрос с задачей
- THEN мост получает `503`
- AND задача не выполняется

### Requirement: Повторный запрос с тем же ключом
Запрос МОЖЕТ содержать ключ повторной постановки. Новый клиент ДОЛЖЕН передавать его;
прежний клиент может не передавать — тогда защита от дублей не действует. Повтор с тем же
ключом возвращает существующую задачу и не создаёт второе выполнение.

#### Scenario: Потерянный ответ
- GIVEN задача с ключом `requestId` уже сохранена
- WHEN приходит повторный запрос с тем же ключом
- THEN ответ содержит прежний идентификатор и признак повтора
- AND очередь не пополняется

#### Scenario: Конфликт ключа
- GIVEN ключ уже связан с другой задачей
- WHEN приходит запрос с тем же ключом и другим текстом
- THEN мост получает `409`
- AND вторая задача не создаётся

#### Scenario: Клиент без ключа
- GIVEN клиент не передаёт ключ повторной постановки
- WHEN он повторяет запрос
- THEN создаётся новая задача
- AND в журнал пишется предупреждение

### Requirement: Ключ из сообщения группы
Для задачи, пришедшей из группы моста в Telegram, ключом повторной постановки ДОЛЖЕН
служить идентификатор сообщения, чтобы повторная доставка апдейта не создавала дубль.

#### Scenario: Повторная доставка апдейта
- GIVEN бот-ассистент отправил задачу в группу
- WHEN тот же апдейт приходит повторно
- THEN задача не дублируется
- AND возвращается прежний идентификатор

### Requirement: Прежний клиент остаётся работоспособным
Изменение приёма НЕ ДОЛЖНО ломать прежний запрос моста: поля `task` и `source` остаются
обязательными и достаточными для старого клиента.

#### Scenario: Старый запрос

## ADDED Requirements

### Requirement: Маршрут ответа сохраняется в задаче
Задача, поступившая через ассистента, ДОЛЖНА сохранять идентификаторы исходного бота и
разговора. Результат и вопросы направляются по этому маршруту.

#### Scenario: Агент запрашивает уточнение
- GIVEN поручение передано через ассистента
- WHEN агенту требуется информация
- THEN вопрос появляется в исходном разговоре
- AND ответ владельца продолжает ту же задачу и сессию

#### Scenario: Отмена без отдельного события
- GIVEN задачу отменили через контракт
- WHEN ассистент хочет узнать состояние
- THEN он получает `cancelled` через `GET /v1/tasks/:id`
- AND пользовательское событие отмены не отправляется

#### Scenario: Чужой маршрут
- GIVEN в запросе указан маршрут, не совпадающий с настроенным ассистентом
- WHEN домен проверяет запрос
- THEN запрос отклоняется
- AND задача не создаётся

### Requirement: Состояние задачи доступно по контракту
Контракт ДОЛЖЕН позволять получить состояние задачи, ответить на вопрос и отменить задачу.
Изменяющие запросы ДОЛЖНЫ быть идемпотентны по `requestId`.

#### Scenario: Получение состояния
- GIVEN задача существует
- WHEN ассистент запрашивает её состояние
- THEN ответ содержит состояние выполнения, состояние доставки и вопрос, если он есть
- AND секреты и внутренние пути в ответ не попадают

#### Scenario: Отмена
- GIVEN задача выполняется или ждёт ответа
- WHEN ассистент отменяет её
- THEN выполнение останавливается, состояние становится «отменена»
- AND повторная отмена с тем же `requestId` возвращает тот же успешный ответ

### Requirement: Идемпотентность запросов
Повтор запроса с тем же `requestId` ДОЛЖЕН возвращать прежний результат и НЕ ДОЛЖЕН
создавать второе выполнение, вторую задачу, второй ответ или вторую отмену. Повтор с тем же
ключом и другим телом — `409`.

#### Scenario: Потерян ответ на постановку
- GIVEN задача сохранена, а ответ потерян
- WHEN ассистент повторяет `/v1/tasks` с тем же `requestId`
- THEN возвращается прежний `taskId` и признак повтора
- AND второго выполнения нет

#### Scenario: Повтор ответа на вопрос
- GIVEN ответ на вопрос уже принят
- WHEN ассистент повторяет `/reply` с тем же `requestId`
- THEN возвращается прежний ответ со статусом `202`
- AND задача не продолжается второй раз

#### Scenario: Конфликт ключа
- GIVEN `requestId` уже связан с другим телом
- WHEN приходит повтор с тем же ключом
- THEN ответ `409`
- AND состояние не меняется

### Requirement: Транспорт файлов по контракту
Входные файлы ДОЛЖНЫ загружаться через `POST /v1/files` (multipart) и передаваться в задаче
по `fileId`; файлы результата ДОЛЖНЫ отдаваться через `GET /v1/files/:id` с токеном в
пределах срока хранения. Размер загрузки ограничен `FILES_MAX_BYTES`.

#### Scenario: Входной файл
- GIVEN ассистент загрузил файл
- WHEN он передаёт `fileId` в задаче
- THEN агент использует этот файл как вложение
- AND произвольный путь или URL вместо `fileId` отклоняется

#### Scenario: Файл результата
- GIVEN задача создала файл
- WHEN событие результата содержит `fileId`
- THEN ассистент скачивает файл с токеном
- AND после истечения срока хранения получает `410`

#### Scenario: Слишком большой файл
- GIVEN размер файла больше `FILES_MAX_BYTES`
- WHEN ассистент загружает его
- THEN ответ `413`
- AND файл не сохраняется

#### Scenario: Чужой файл
- GIVEN `fileId` не выдавался этому ассистенту
- WHEN он передаёт его в задаче
- THEN запрос отклоняется
- AND файл не читается

### Requirement: Служебные события без сообщения пользователю
Служебные события (например, `memory_proposal`) ДОЛЖНЫ доставляться только если ассистент
объявил поддержку (`capabilities.serviceEvents`), не иметь полей пользовательского текста и
НЕ ДОЛЖНЫ создавать сообщение в разговоре.

#### Scenario: Предложение памяти
- GIVEN агент предлагает ассистенту сохранить рабочий факт
- WHEN событие доставляется
- THEN в нём есть `proposal` и нет `text`/`title` пользовательского сообщения
- AND ассистент сам решает, создавать ли запись

#### Scenario: Старый приёмник
- GIVEN ассистент не объявил поддержку служебных событий
- WHEN у агента появляется предложение памяти
- THEN событие не отправляется
- AND это не считается ошибкой доставки

### Requirement: Подтверждение обработки события
Событие доставки ДОЛЖНО иметь постоянный идентификатор формата
`<taskId>:<type>:<version>` без sequence. Получатель ДОЛЖЕН подтверждать обработку; агент
ДОЛЖЕН прекращать повторы после подтверждения и повторять с тем же идентификатором до него.

#### Scenario: Повтор события
- GIVEN ассистент уже обработал событие результата
- WHEN агент присылает его повторно
- THEN ассистент подтверждает обработку и не создаёт повторное сообщение
- AND агент отмечает доставку подтверждённой

#### Scenario: Нет подтверждения
- GIVEN ассистент принял событие, но не подтвердил обработку
- WHEN подходит время повтора
- THEN агент отправляет событие с тем же идентификатором
- AND не запускает задачу повторно

### Requirement: Ревизия результата по контракту
Контракт ДОЛЖЕН позволять запросить доработку результата с сохранением связи с исходной
задачей.

#### Scenario: Изменение документа
- GIVEN агент выдал документ
- WHEN владелец просит изменить конкретный раздел
- THEN создаётся новая версия задачи с прежним результатом на входе
- AND прежняя версия и её файлы остаются доступными согласно сроку хранения

### Requirement: Возможности и версия контракта
Домен ДОЛЖЕН сообщать поддерживаемую версию контракта и набор возможностей, чтобы обе
стороны могли выбрать совместимый режим.

#### Scenario: Согласование версии
- GIVEN ассистент подключается к агенту
- WHEN он запрашивает `/v1/capabilities`
- THEN ответ содержит версию контракта, файлы, ревизии и служебные события
- AND при отсутствии версии 2 используется прежний режим

### Requirement: Задача от ассистента не расширяет права
Задача, поступившая по контракту, ДОЛЖНА выполняться по той же политике, что и личная:
разрешённая рабочая папка и `cwd`, запрет сети, секретов и серверов. Подлинность запроса
ассистента НЕ ДОЛЖНА давать дополнительных операций.

#### Scenario: Попытка выйти за политику
- GIVEN задача просит доступ к сети, секрету или серверу
- WHEN она выполняется
- THEN действует та же политика, что и для личной задачи
- AND запрос отклоняется или выполняется в тех же ограничениях

#### Scenario: Проверка тестом
- GIVEN есть тест границ задачи
- WHEN задача пришла от ассистента
- THEN тест подтверждает те же ограничения, что и для личной задачи
- AND расхождений нет

## ADDED Requirements

### Requirement: Факты ассистента приходят в задаче
Запрос задачи по контракту МОЖЕТ содержать отобранные ассистентом факты — массив объектов
`{ text, subject?, validUntil? }`. Домен ДОЛЖЕН проверить число фактов (до 50), длину
текста (до 300 символов), длину `subject` (до 60) и корректность даты; невалидный элемент
отклоняет запрос. Факты используются только в этой задаче и НЕ сохраняются как память
агента.

#### Scenario: Факты для задачи
- GIVEN ассистент передал `context.facts` объектами
- WHEN задача выполняется
- THEN факты используются в промпте этой задачи
- AND после завершения не остаются в памяти агента

#### Scenario: Невалидный факт
- GIVEN в `context.facts` элемент без текста, слишком длинный или с некорректной датой
- WHEN домен проверяет запрос
- THEN ответ `400`, задача не создаётся
- AND ошибка не раскрывает значения фактов

#### Scenario: Пустой контекст
- GIVEN ассистент не передал факты
- WHEN задача выполняется
- THEN используются только рабочие факты агента
- AND поведение не меняется

### Requirement: Предложение рабочей памяти
Рабочие факты, которые агент хочет сохранить, ДОЛЖНЫ уходить ассистенту service-событием
`memory_proposal` с постоянным `eventId` формата `<taskId>:memory_proposal:<версия>` и
подтверждением обработки; в событии есть `proposal` и нет полей пользовательского текста
(`text`/`title`). Событие отправляется только если ассистент объявил
`capabilities.serviceEvents: true`; иначе оно не отправляется и не считается ошибкой
доставки. Решение о долговременной записи личных фактов принимает ассистент. При
недоступности ассистента событие ждёт в очереди доставки и не применяется агентом молча.

#### Scenario: Предложение сохранить факт
- GIVEN агент вывел устойчивый рабочий факт
- WHEN он хочет сохранить его навсегда
- THEN событие `memory_proposal` уходит по контракту
- AND агент не записывает личный факт молча

#### Scenario: Ассистент без поддержки
- GIVEN ассистент не объявил `capabilities.serviceEvents`
- WHEN у агента появляется предложение памяти
- THEN событие не отправляется
- AND это не считается ошибкой доставки

#### Scenario: Повтор service-события
- GIVEN ассистент уже обработал `memory_proposal`
- WHEN событие приходит повторно с тем же `eventId`
- THEN ассистент подтверждает обработку и не показывает сообщение
- AND агент не создаёт второе предложение

### Requirement: Владение памятью описано в контракте
Контракт ДОЛЖЕН фиксировать: личные факты принадлежат ассистенту, рабочий контекст задач и
предпочтения для работы — агенту; обновления личной памяти идут только через согласованный
интерфейс (`context.facts`, `memory_proposal`, `ack`).

#### Scenario: Проверка владельца
- GIVEN агент получил личный факт от ассистента
- WHEN факт нужен другой задаче
- THEN агент не хранит его между задачами
- AND запрашивает актуальные факты у ассистента в новой задаче
