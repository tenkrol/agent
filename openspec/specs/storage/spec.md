# Спека домена storage

## ADDED Requirements

### Requirement: Состояние пишет только домен storage
Запись файлов состояния ДОЛЖНА происходить внутри `src/storage/`. Остальные домены
получают готовые хранилища через публичный API домена.

#### Scenario: Запись в обход домена
- GIVEN в `src/` вне `src/storage/` появляется запись файла состояния
- WHEN запускается сторожевой тест
- THEN тест падает и указывает файл

### Requirement: Запись атомарна
Запись ДОЛЖНА идти через временный файл и переименование, чтобы сбой посреди записи не
оставлял пустой или частичный файл состояния; временные файлы не остаются после успеха.

Для append-only журналов (`tasks.jsonl`, `actions.jsonl`) допускается дописывание строки с
`fsync` на границах состояния: последняя неполная строка при загрузке пропускается, а
предыдущие записи сохраняются. Это исключение не отменяет атомарность JSON-файлов состояния
и не разрешает частичную перезапись файла.

#### Scenario: Успешная запись
- GIVEN хранилище сохраняет состояние
- WHEN запись завершена
- THEN файл читается как валидный JSON
- AND рядом не осталось временных файлов

#### Scenario: Сбой посреди строки журнала
- GIVEN процесс упал посреди дописывания строки в `tasks.jsonl`
- WHEN журнал загружается
- THEN неполная последняя строка пропускается
- AND все предыдущие записи читаются

### Requirement: Битый файл откладывается, а не теряется
Если файл не читается как JSON или имеет незнакомую версию, ДОЛЖНА оставаться его копия
`<файл>.corrupt-<дата>`, и только после этого работа продолжается с пустым состоянием.

#### Scenario: Повреждённый JSON
- GIVEN файл состояния повреждён
- WHEN хранилище загружается
- THEN копия повреждённого файла сохранена рядом
- AND агент стартует с пустым состоянием и пишет об этом в журнал

### Requirement: Версия схемы проверяется
Хранилище ДОЛЖНО проверять поле версии: читать версию 2, переносить версию 1 и откладывать
файл незнакомой (более новой) версии в копию `memory.json.corrupt-<дата>`, не принимая его
за валидный.

#### Scenario: Файл версии 2
- GIVEN файл памяти содержит версию 2
- WHEN хранилище загружается
- THEN факты читаются в новой схеме
- AND файл не перезаписывается без изменений

#### Scenario: Файл будущей версии
- GIVEN файл содержит версию новее, чем понимает код
- WHEN хранилище загружается
- THEN файл откладывается в копию
- AND память стартует пустой, данные не подменяются молча

### Requirement: Принятая задача записывается долговечно
Журнал задач ДОЛЖЕН обеспечивать долговечную запись принятой задачи: после успешного
ответа вызывающий код может быть уверен, что запись переживёт перезапуск процесса.
Отметки прогресса могут оставаться отложенными, но принятие задачи, каждая смена состояния
и финальный статус — нет.

#### Scenario: Долговечное принятие
- GIVEN задача принимается
- WHEN запись возвращает успех
- THEN данные записаны и подтверждены на диске
- AND повторный запуск процесса видит эту задачу

#### Scenario: Ошибка записи
- GIVEN диск недоступен или кончилось место
- WHEN журнал пытается сохранить принятую задачу
- THEN операция завершается ошибкой
- AND вызывающий код не получает успешного результата

### Requirement: Журнал переходов
Каждая запись задачи ДОЛЖНА хранить переходы состояния с временем и причиной. История
переходов не должна теряться при перезаписи журнала.

#### Scenario: Смена состояния
- GIVEN задача меняет состояние
- WHEN переход сохраняется
- THEN в записи появляется отметка времени, прежнее и новое состояние, причина
- AND после перезапуска история переходов доступна

### Requirement: Восстановление состояния после загрузки
Хранилище ДОЛЖНО предоставлять восстановление: задачи в очереди, незавершённые выполнения
и ожидание владельца. Загрузка не должна сама менять поведение без явного вызова
восстановления.

#### Scenario: Незавершённое выполнение
- GIVEN журнал содержит задачу в состоянии выполнения
- WHEN выполняется восстановление
- THEN задача помечается как прерванная
- AND сохраняются последние известные промежуточные данные

### Requirement: Ключи повторных запросов уникальны
Хранилище ДОЛЖНО хранить ключ повторного запроса вместе с задачей и находить задачу по
ключу после перезапуска. Один ключ не может соответствовать двум задачам.

#### Scenario: Повтор после перезапуска
- GIVEN задача с ключом сохранена
- WHEN процесс перезапускается и приходит тот же ключ
- THEN хранилище возвращает прежнюю задачу
- AND новая запись не создаётся

### Requirement: Журнал внешних действий
Хранилище ДОЛЖНО вести журнал внешних действий с состояниями «начато», «подтверждено»,
«неизвестно» и уметь возвращать незавершённые действия по задаче.

#### Scenario: Сбой между началом и подтверждением
- GIVEN действие записано как начатое
- AND подтверждение не записано
- WHEN задача восстанавливается
- THEN действие считается неизвестным
- AND повтор действия требует решения владельца

### Requirement: Совместимость схемы журнала
Хранилище ДОЛЖНО читать прежнюю версию журнала задач и переносить старые статусы в новые
состояния без потери записей.

#### Scenario: Журнал прежней версии
- GIVEN на диске журнал задач версии 1
- WHEN агент загружается после обновления
- THEN записи читаются и переносятся в новую схему
- AND задачи не теряются и не объявляются заново выполненными

## ADDED Requirements

### Requirement: Критерии и результат проверки в записи задачи
Запись задачи ДОЛЖНА хранить критерии результата и результат проверки: статус, результаты
по критериям, доказательства, ограничения и число попыток.

#### Scenario: Задача проверена
- GIVEN проверка завершена
- WHEN запись задачи сохраняется
- THEN критерии и результат проверки доступны после перезапуска
- AND `/task <id>` может показать, что проверено

### Requirement: Совместимость старых записей
Записи без критериев и результата проверки ДОЛЖНЫ читаться как задачи, выполненные до
появления проверки, без ошибок загрузки.

#### Scenario: Старая задача
- GIVEN запись создана до обновления
- WHEN журнал загружается
- THEN запись читается
- AND новые поля считаются отсутствующими

## ADDED Requirements

### Requirement: Журнал доставки событий
Хранилище ДОЛЖНО вести постоянный журнал событий доставки: идентификатор события, тип,
маршрут и канал (`assistant` или личный чат), содержимое, состояние, число и время попыток,
подтверждение обработки.

#### Scenario: Сохранение события
- GIVEN событие результата сформировано
- WHEN оно ставится в очередь доставки
- THEN запись сохраняется до первой попытки отправки
- AND после перезапуска незавершённая доставка видна и может быть продолжена

#### Scenario: Подтверждение
- GIVEN событие отправлено
- WHEN получатель подтвердил обработку
- THEN в журнале отмечается подтверждение и время
- AND повторная отправка не планируется

#### Scenario: Незавершённая отправка
- GIVEN запись осталась в состоянии `sending`
- WHEN хранилище загружается
- THEN запись не считается зависшей
- AND исход помечается как неизвестный, повтор разрешён по правилам доставки

### Requirement: Ключи запросов по областям
Хранилище ДОЛЖНО хранить ключи идемпотентности изменяющих запросов (`requestKeys`) с
областью `submit`, `reply` или `cancel` и находить по ним прежний результат после
перезапуска. Ключ постановки хранится в записи задачи (PLA-13), ключи ответа и отмены — в
журнале ключей запросов. Один ключ в одной области не может соответствовать двум разным
запросам.

#### Scenario: Повтор постановки
- GIVEN задача с ключом `submit` сохранена
- WHEN приходит тот же ключ
- THEN хранилище возвращает прежний `taskId`
- AND новая запись не создаётся

#### Scenario: Повтор ответа
- GIVEN ответ на вопрос с ключом `reply` сохранён
- WHEN приходит тот же ключ
- THEN хранилище возвращает прежний результат ответа
- AND задача не продолжается второй раз

#### Scenario: Повтор отмены
- GIVEN отмена с ключом `cancel` сохранена
- WHEN приходит тот же ключ
- THEN хранилище возвращает прежний успешный результат
- AND повторная отмена не выполняется

#### Scenario: Конфликт ключа
- GIVEN ключ уже связан с другим телом запроса
- WHEN приходит тот же ключ
- THEN хранилище сообщает конфликт
- AND данные не меняются

### Requirement: Реестр файлов
Хранилище ДОЛЖНО вести реестр файлов контракта: непрозрачный `fileId`, имя, тип, размер,
направление (`input` или `result`), путь хранения, время создания и срок хранения.

#### Scenario: Загруженный файл
- GIVEN файл загружен через контракт
- WHEN задача ссылается на `fileId`
- THEN реестр отдаёт путь и метаданные
- AND файл вне рабочей папки задачи не читается

#### Scenario: Файл результата
- GIVEN задача создала файл результата
- WHEN он регистрируется
- THEN запись сохраняется и переживает перезапуск
- AND файл доступен до истечения срока хранения, после — недоступен

#### Scenario: Истёкший срок
- GIVEN срок хранения файла истёк
- WHEN запрашивается `fileId`
- THEN файл не отдаётся
- AND запись реестра помечается истёкшей

### Requirement: Маршрут и версия в записи задачи
Запись задачи ДОЛЖНА хранить маршрут ответа, номер версии результата, корневую задачу и
связь ревизии.

#### Scenario: Задача из ассистента
- GIVEN задача поступила по контракту с маршрутом
- WHEN запись сохраняется
- THEN маршрут и версия сохранены вместе с задачей
- AND после перезапуска они доступны без обращения к ассистенту

#### Scenario: Прежняя запись
- GIVEN запись создана до обновления
- WHEN журнал загружается
- THEN маршрут считается личным чатом агента
- AND версия равна 1, корневая задача равна самой задаче

### Requirement: История версий результата
Хранилище ДОЛЖНО сохранять связь между версиями одной задачи и не терять прежние записи
до истечения срока хранения.

#### Scenario: Новая версия
- GIVEN у задачи есть результат версии 1
- WHEN создаётся ревизия
- THEN обе записи сохраняются
- AND по корневой задаче можно найти все версии

## ADDED Requirements

### Requirement: Хранение процедур с версиями
Хранилище ДОЛЖНО вести `procedures.json` с атомарной записью, версией схемы и историей
версий процедур вместе с их статусом (`draft`, `active`, `archived`).

#### Scenario: Сохранение версии
- GIVEN создаётся новая версия процедуры
- WHEN запись завершена
- THEN версия сохранена со своим статусом, прежние версии не изменены
- AND после перезапуска доступны все версии

#### Scenario: Битый файл
- GIVEN файл процедур повреждён
- WHEN хранилище загружается
- THEN копия повреждённого файла сохранена рядом
- AND агент стартует с пустым списком и пишет об этом в журнал

### Requirement: Версия схемы файла процедур проверяется
Хранилище ДОЛЖНО проверять версию схемы файла процедур и не принимать незнакомую версию
как валидную. Это отдельная проверка от версии самой процедуры.

#### Scenario: Файл будущей версии
- GIVEN файл содержит версию схемы новее, чем понимает код
- WHEN хранилище загружается
- THEN файл откладывается в копию
- AND данные не подменяются

### Requirement: Черновики и активные версии различаются
Хранилище ДОЛЖНО хранить статус каждой версии и не выдавать черновик как действующую
версию. `activeVersion` процедуры НЕ ДОЛЖЕН указывать на `draft`.

#### Scenario: Черновик в файле
- GIVEN в файле есть версия со статусом `draft`
- WHEN процедура загружается
- THEN она не считается активной
- AND `run` получает отказ с перечнем недостающих полей

#### Scenario: Активация
- GIVEN черновик заполнен
- WHEN версия активируется
- THEN статус меняется на `active`
- AND `activeVersion` указывает на неё

### Requirement: Срок и число версий ограничены
Хранилище ДОЛЖНО соблюдать `PROCEDURES_MAX_VERSIONS` и `PROCEDURES_RETENTION_DAYS`: удалять
старые архивные версии и удалённые процедуры по сроку, не теряя версию, на которую
ссылается задача.

#### Scenario: Старая задача
- GIVEN задача ссылается на версию процедуры
- WHEN наступает уборка старых версий
- THEN используемая задачами версия не удаляется
- AND снимок версии в задаче остаётся доступен

#### Scenario: Предел числа версий
- GIVEN у процедуры больше версий, чем `PROCEDURES_MAX_VERSIONS`
- WHEN выполняется уборка
- THEN удаляются самые старые архивные версии
- AND активная версия и версии, на которые ссылаются задачи, сохраняются

## ADDED Requirements

### Requirement: Виды памяти различаются
Хранилище ДОЛЖНО различать постоянные предпочтения, временные сведения и контекст задачи.
Долговременная запись ДОЛЖНА иметь источник, дату, область применения и при необходимости
срок актуальности. Хранилище агента содержит только его собственную память: рабочий
контекст задач и предпочтения, явно сообщённые владельцем агенту; личные факты ассистента в
нём НЕ хранятся.

#### Scenario: Временное сведение
- GIVEN сохраняется временный факт со сроком
- WHEN срок истёк
- THEN факт не считается действующим
- AND остаётся в истории

#### Scenario: Контекст задачи
- GIVEN факт относится к задаче
- WHEN задача закрыта и срок хранения истёк
- THEN факт не попадает в другие задачи
- AND удаляется по правилам хранения

#### Scenario: Факт ассистента
- GIVEN ассистент передал личный факт для задачи
- WHEN задача завершена
- THEN факт не записан в `memory.json`
- AND другие задачи его не видят

### Requirement: Исправление устаревшего факта
Новый факт с тем же предметом и областью ДОЛЖЕН становиться действующим, а прежний —
переводиться в историю. Прежний факт НЕ ДОЛЖЕН использоваться как актуальный, изменение
ДОЛЖНО быть доступно для просмотра.

#### Scenario: Новый часовой пояс
- GIVEN в памяти сохранён часовой пояс владельца
- WHEN владелец явно сообщает новый
- THEN новая запись становится действующей
- AND предыдущая не используется как актуальная
- AND изменение доступно для просмотра

### Requirement: История памяти сохраняется
Хранилище ДОЛЖНО сохранять заменённые и истёкшие факты для просмотра и объяснения
поведения, не используя их в задачах. Предел истории — `MEMORY_HISTORY_MAX`.

#### Scenario: Просмотр истории
- GIVEN факт был заменён
- WHEN владелец запрашивает историю
- THEN видны новый и прежний факты с датами и источником
- AND в промпт попадает только действующий

### Requirement: Отбор памяти для задачи
Хранилище ДОЛЖНО отбирать для задачи только действующие, неистёкшие и относящиеся к ней
факты в пределах бюджета `MEMORY_CONTEXT_CHARS` и предела `MEMORY_MAX_FACTS`.

#### Scenario: Чужая область
- GIVEN факт относится к другому чату или задаче
- WHEN собирается память для текущей задачи
- THEN факт не попадает в результат
- AND бюджет соблюдается

### Requirement: Секреты не попадают в память и не показываются
Хранилище НЕ ДОЛЖНО сохранять значения секретов. Попытка записи такого факта отклоняется,
в журнал попадает только имя ключа, без значения. При выдаче памяти (список и история)
значения секретов ДОЛЖНЫ вырезаться или факт скрываться, даже если он оказался в файле до
обновления. Проверка выполняется связанным guard-портом домена `secrets`; порт создаётся в
точке сборки из `config`, значения секретов в хранилище не передаются, шифртекст и
окружение хранилище не читает.

#### Scenario: Факт с ключом
- GIVEN факт содержит значение известного секрета
- WHEN он добавляется
- THEN запись отклоняется
- AND значение не сохраняется и не логируется

#### Scenario: Секрет в старом факте
- GIVEN в файле уже есть факт со значением секрета
- WHEN владелец открывает `/memory` или историю
- THEN значение не показывается
- AND видно, что факт скрыт как содержащий секрет, без значения

### Requirement: Миграция памяти
Хранилище ДОЛЖНО переносить память версии 1 в схему версии 2: до миграции создавать копию
`memory.json.v1.bak`, после миграции сразу записывать файл с `version: 2`, а при сбое записи
сохранять исходный файл и копию для повторной попытки. Старые факты ДОЛЖНЫ проходить скан
секретов: найденные не переносятся, в истории остаётся пометка без значения.

#### Scenario: Первый запуск после обновления
- GIVEN на диске память версии 1
- WHEN агент загружается
- THEN создана копия `memory.json.v1.bak`
- AND факты перенесены, файл сразу записан как версия 2
- AND факты с секретами не перенесены

#### Scenario: Сбой записи при миграции
- GIVEN миграция не смогла записать файл
- WHEN агент продолжает работу
- THEN исходный файл и `.v1.bak` на месте
- AND при следующем старте миграция повторяется

### Requirement: Откат памяти проверяется
Откат на предыдущую версию ДОЛЖЕН выполняться восстановлением `memory.json.v1.bak` до
запуска старого кода, потому что старый код версию не проверяет и перезаписывает файл как
версию 1.

#### Scenario: Откат релиза
- GIVEN память мигрирована на версию 2
- WHEN выполняется откат на предыдущий релиз
- THEN `.v1.bak` восстанавливается на место `memory.json`
- AND старый код видит прежние факты

## ADDED Requirements

### Requirement: Транзакционная очередь с арендой
Очередь ДОЛЖНА хранить задачи транзакционно, выдавать аренду с `generation` и
отвергать результат устаревшей попытки.

#### Scenario: Два работника
- GIVEN в очереди одна задача
- WHEN два работника одновременно пытаются её захватить
- THEN задачу получает ровно один
- AND второй получает «нет работы».

#### Scenario: Устаревшая попытка
- GIVEN задача была перезахвачена с новым `generation`
- WHEN старая попытка пытается её завершить
- THEN запись отвергается
- AND задача не получает ложный терминальный статус.

#### Scenario: Потеря работника
- GIVEN аренда истекла, heartbeat не приходит
- WHEN другой работник захватывает задачу
- THEN создаётся новая попытка
- AND прежняя помечается потерянной.

### Requirement: Fencing завершения
Завершить задачу МОЖЕТ только владелец аренды с актуальным generation и живой арендой;
повторный terminal и результат после потери аренды отвергаются.

#### Scenario: Потеря аренды
- GIVEN аренда истекла и задача перезахвачена
- WHEN старая попытка завершает done
- THEN запись отвергается
- AND новая попытка продолжает владеть задачей.
