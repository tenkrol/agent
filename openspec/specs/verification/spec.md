# Спека домена verification

## ADDED Requirements

### Requirement: Критерии выводятся из запроса
Домен ДОЛЖЕН выводить проверяемые критерии результата из формулировки владельца и типа
результата. Критерий ДОЛЖЕН ссылаться на фразу запроса или на минимальную проверку типа;
придумывать новые требования запрещено.

#### Scenario: Формат и разделы
- GIVEN владелец указал формат и обязательные разделы
- WHEN строятся критерии
- THEN критерии покрывают формат и разделы
- AND не добавляют разделов, которых владелец не просил

#### Scenario: Источники
- GIVEN владелец требует источники
- WHEN строится критерий
- THEN наличие источников становится обязательным критерием
- AND проверка ссылается на этот критерий

### Requirement: Минимальные проверки по типу результата
Домен ДОЛЖЕН применять минимальные проверки, соответствующие результату:

| Результат | Минимальная проверка |
|---|---|
| Документ | Файл открывается, содержит требуемые разделы; при значимых требованиях к оформлению проверяется отображение |
| Таблица | Каждый файл открывается, нужные данные присутствуют, применимые формулы пересчитаны и проверены |
| Изменение кода | Выполнены подходящие проверки; результат и ограничения зафиксированы |
| Исследование | Выводы связаны с источниками, предположения отделены от подтверждённых сведений |

#### Scenario: Второй файл повреждён
- GIVEN результат содержит две таблицы
- WHEN первая проходит проверку, а вторая не открывается
- THEN итог проверки не равен «пройдена»
- AND свидетельство называет проблемный файл

### Requirement: Команды проверок ограничены allowlist
Для изменения кода домен ДОЛЖЕН использовать только команды из allowlist
(`VERIFY_CHECK_ALLOWLIST`): типовые проверки известных типов проектов (тесты, линтер,
сборка). Команда вне allowlist, произвольная shell-строка или составная команда НЕ ДОЛЖНЫ
запускаться; критерий получает статус «недоступна» с причиной, а не «пройдено». Пустой
allowlist означает, что проверки кода недоступны.

#### Scenario: Разрешённая проверка
- GIVEN критерий требует тестов, и команда есть в allowlist
- WHEN домен строит проверку
- THEN команда передаётся порту `execution` как argv
- AND оболочка не используется

#### Scenario: Команда вне allowlist
- GIVEN модель предложила команду, которой нет в allowlist
- WHEN домен выбирает проверку
- THEN команда не запускается
- AND критерий получает статус «недоступна» с причиной «команда не разрешена»

#### Scenario: Пустой allowlist
- GIVEN `VERIFY_CHECK_ALLOWLIST` пуст
- WHEN требуется проверка кода
- THEN проверка считается недоступной
- AND это не превращается в успешный статус

### Requirement: Статусы проверки
Проверка ДОЛЖНА возвращать статус «пройдена», «провалена», «частично», «недоступна»,
«не требуется» или «отключена» и список результатов по каждому критерию с доказательством.
Статус «отключена» используется только когда проверка выключена настройкой `VERIFY=false`, и
всегда несёт причину.

#### Scenario: Недоступная проверка
- GIVEN окружение не позволяет выполнить проверку
- WHEN домен возвращает результат
- THEN статус «недоступна» и причина в ограничениях
- AND это не считается успешной проверкой

#### Scenario: Проверка отключена
- GIVEN проверка выключена настройкой
- WHEN домен формирует результат
- THEN статус «отключена» с причиной `VERIFY=false`
- AND отчёт явно помечает это, а не выдаёт за пройденную проверку

#### Scenario: Проверка не требуется
- GIVEN результат не относится к проверяемым типам и дополнительных критериев нет
- WHEN домен формирует результат
- THEN статус «не требуется»
- AND это не смешивается с «недоступна» и не даёт `partial`

### Requirement: Проверка не выдаёт результат за проверенный
Домен НЕ ДОЛЖЕН возвращать успешный статус, если обязательный критерий не проверен или
провален.

#### Scenario: Нет доказательства
- GIVEN по критерию нет доказательства
- WHEN итог вычисляется
- THEN статус не «пройдена»
- AND причина попадает в ограничения

## ADDED Requirements

### Requirement: Пересчёт таблицы должен быть подтверждён
Критерий вычислений ДОЛЖЕН получать «пройден», только если пересчёт каждого табличного
файла подтверждён успешным результатом и в файле нет ошибок формул. Пустой массив ошибок
при неуспешном пересчёте не подтверждает вычисления.

#### Scenario: LibreOffice недоступен
- GIVEN таблица открывается и содержит данные
- WHEN пересчёт возвращает «не выполнено» и причину
- THEN критерий вычислений «недоступен»
- AND итог проверки не равен «пройдена»
- AND отчёт указывает, что формулы не пересчитаны

#### Scenario: Пересчёт выбросил исключение
- GIVEN таблица требует пересчёта
- WHEN порт пересчёта падает или превышает таймаут
- THEN ошибка не превращается в пустой успешный результат
- AND итог проверки не равен «пройдена»

#### Scenario: Ошибка формулы
- GIVEN при чтении обнаружена ошибка `#REF!`
- WHEN пересчёт недоступен
- THEN обнаруженная ошибка сохраняется в свидетельстве
- AND не заменяется утверждением «ошибок формул нет»

#### Scenario: Пересчёт исправил ошибку
- GIVEN исходный файл содержал ошибку формулы
- WHEN пересчёт стал успешным, но проверенная версия не сохранена и не выдана
- THEN критерий вычислений «провален»
- AND в свидетельстве есть исходная ошибка и пометка об отсутствии сохранённой версии

### Requirement: Вердикт исследования структурирован
Проверяющая модель ДОЛЖНА возвращать структурированный JSON-вердикт по независимым
критериям: наличие источников, связь выводов с источниками, отделение предположений.
Каждый критерий содержит статус и краткое обоснование. Ответ ДОЛЖЕН проходить проверку
схемы; ключевые слова в тексте ответа не являются доказательством.

#### Scenario: Все критерии отклонены
- GIVEN ответ содержит фразу «Источники отсутствуют»
- WHEN проверяющая модель отклоняет критерии
- THEN ни один критерий не получает «пройден» из-за ключевого слова
- AND итог не равен «пройдена»

#### Scenario: Источники есть, связь не установлена
- GIVEN в ответе есть список ссылок
- WHEN вердикт не подтверждает связь выводов с источниками
- THEN критерий связи не получает «пройден»
- AND общий итог не «пройдена»

#### Scenario: Вердикт не разобран
- GIVEN модель вернула некорректный JSON, неизвестный статус или пропустила поле
- WHEN вердикт обрабатывается
- THEN непроверенные критерии «недоступны»
- AND итог не равен «пройдена»

### Requirement: Границы проверки источников обозначены
Система ДОЛЖНА различать оценку структуры ответа и фактическую проверку содержимого
источников. Без чтения источников проверка не ДОЛЖНА представляться как фактчекинг.

#### Scenario: Доступен только текст ответа
- GIVEN проверяющая модель получила текст ответа без содержимого источников
- WHEN формируется отчёт
- THEN ограничение «фактическая проверка источников не выполнялась» указано явно
- AND итог не выдаётся за независимый фактчекинг

## ADDED Requirements

### Requirement: Проверка прерывается отменой
Проверка ДОЛЖНА принимать сигнал отмены и передавать его всем портам: модели,
LibreOffice, запуску тестов. При уже отменённом сигнале порты не вызываются; поздний
ответ не меняет терминальный исход.

#### Scenario: Отмена до модели
- GIVEN сигнал уже отменён
- WHEN вызывается проверка исследования
- THEN модельный порт не вызывается
- AND проверка не выдаёт `passed`.

#### Scenario: Отмена во время пересчёта
- GIVEN идёт LibreOffice
- WHEN сигнал отменяется
- THEN процесс убивается
- AND проверка завершается без ложного успеха.

### Requirement: Расход проверки учитывается
Проверяющая модель ДОЛЖНА возвращать usage вместе с текстом; расход проверки входит в
общий бюджет задачи.

#### Scenario: Учёт модели
- GIVEN модель вернула usage
- WHEN проверка завершилась
- THEN оркестратор вычитает этот расход из остатка.
