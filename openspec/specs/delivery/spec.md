# Спека домена delivery

## ADDED Requirements

### Requirement: Как выглядит ответ — решает домен
Сборка текста ответа (заголовок, тело, диагностика, подпись, заметки) ДОЛЖНА происходить в
домене `delivery` из готовых данных. Ядро не склеивает текст ответа вручную.

#### Scenario: Обычная задача
- GIVEN задача завершилась успешно
- WHEN формируется ответ
- THEN домен собирает текст и подпись со стоимостью
- AND ядро передаёт только числа

### Requirement: Условия заголовка сохраняются
Заголовок ДОЛЖЕН различать отмену, превышение шагов, превышение бюджета, таймаут и код
ошибки ровно так же, как раньше.

#### Scenario: Лимит шагов
- GIVEN задача остановлена по лимиту шагов
- WHEN домен строит заголовок
- THEN в тексте есть причина и совет сузить задачу
- AND статус задачи не подменяется на «выполнена»

### Requirement: Длина ответа ограничена
Длинный ответ ДОЛЖЕН обрезаться до предела из настроек с пометкой об обрезке.

#### Scenario: Очень длинный ответ
- GIVEN ответ больше предела
- WHEN домен собирает текст
- THEN текст обрезан и помечен
- AND остальные части отчёта сохранены

### Requirement: Домен не зависит от других доменов
Сборка текста ДОЛЖНА использовать только переданные данные: числа, флаги и строку
стоимости. Импортов других доменов в `src/delivery/` быть не должно.

#### Scenario: Проверка границ
- GIVEN в домен добавляют импорт стоимости из `storage`
- WHEN запускается сторожевой тест
- THEN тест падает и указывает файл

## ADDED Requirements

### Requirement: Блок проверки в отчёте
Отчёт ДОЛЖЕН содержать результат проверки: что проверено, что не проверено и почему.
Результат с непроверенными обязательными критериями НЕ ДОЛЖЕН выглядеть как полностью
проверенный.

#### Scenario: Проверка пройдена
- GIVEN обязательные критерии выполнены
- WHEN собирается отчёт
- THEN есть строка «Проверка: …» с перечнем пройденного
- AND заголовок соответствует успешному завершению

#### Scenario: Проверка недоступна
- GIVEN проверку выполнить не удалось
- WHEN собирается отчёт
- THEN есть строка «Не проверено: …» с причиной
- AND заголовок не утверждает полную проверку

#### Scenario: Проверка отключена
- GIVEN ядро передаёт `verification.status = disabled` (`VERIFY=false`)
- WHEN собирается отчёт
- THEN есть явная строка «Проверка отключена (VERIFY=false)»
- AND результат не выглядит проверенным

#### Scenario: Проверка не требуется
- GIVEN ядро передаёт `verification.status = not_required`
- WHEN собирается отчёт
- THEN есть строка «Проверка не требуется для этого результата»
- AND это не подаётся как «не проверено»

### Requirement: Заголовок частичного результата
Отчёт о частичном результате ДОЛЖЕН явно отличаться от отчёта об успехе и называть
проваленные критерии.

#### Scenario: Частичный результат
- GIVEN задача завершена частично
- WHEN домен строит текст
- THEN заголовок говорит о частичном выполнении
- AND перечислены проваленные или непроверенные критерии

### Requirement: Проверка не подменяет состояния
Текст отчёта ДОЛЖЕН строиться из переданного состояния и результата проверки; домен
НЕ ДОЛЖЕН сам решать, выполнена задача или нет.

#### Scenario: Передан частичный результат
- GIVEN ядро передаёт статус «завершена частично» и результат проверки
- WHEN домен собирает текст
- THEN текст соответствует переданному статусу
- AND домен не пересчитывает проверки

## ADDED Requirements

### Requirement: Доставка учитывается отдельно от выполнения
Система ДОЛЖНА отдельно хранить состояние выполнения задачи и доставки её результата.

#### Scenario: Мессенджер недоступен
- GIVEN задача выполнена
- WHEN отправить результат невозможно
- THEN результат сохраняется
- AND доставка повторяется с ограниченной частотой
- AND исполнение задачи заново не запускается

#### Scenario: Успешная доставка
- GIVEN результат готов
- WHEN доставка подтверждена получателем
- THEN состояние доставки становится «подтверждено»
- AND состояние выполнения остаётся «завершена»

### Requirement: Личная доставка в Telegram учитывается отдельно
Доставка результата в личный чат агента ДОЛЖНА учитываться так же, как доставка ассистенту:
состояние, число и время попыток, ограниченный повтор. Ошибка личной доставки НЕ ДОЛЖНА
менять состояние выполнения задачи.

#### Scenario: Telegram недоступен
- GIVEN результат готов, а Telegram не отвечает
- WHEN личная доставка не удалась
- THEN попытки ограничены по числу и частоте
- AND задача остаётся выполненной, результат сохранён
- AND после восстановления связи доставка повторяется

#### Scenario: Повтор не создаёт задачу заново
- GIVEN личная доставка повторяется
- WHEN воркер отправляет сообщение
- THEN исполнитель задачи не запускается
- AND состояние выполнения не меняется

### Requirement: Восстановление незавершённой доставки после рестарта
Запись доставки в состоянии `sending`, найденная при старте, НЕ ДОЛЖНА зависать: агент
считает исход неизвестным (`sent`, подтверждение не получено), не блокирует задачу и
продолжает доставку по правилам повторов.

#### Scenario: Сбой в момент отправки
- GIVEN процесс упал после начала отправки
- AND подтверждение не сохранено
- WHEN сервис стартует
- THEN запись не остаётся в `sending`
- AND исход считается неизвестным, доставка не зависает
- AND повтор выполняется по ограниченному расписанию

### Requirement: Уведомление о неуспешной доставке
Если доставка события ассистенту окончательно не удалась, владелец ДОЛЖЕН получить
уведомление в личном чате агента. Канал ассистента в этот момент может быть недоступен,
поэтому уведомление идёт другим каналом и не зависит от него.

#### Scenario: Ассистент недоступен
- GIVEN все попытки доставки ассистенту исчерпаны
- WHEN доставка помечена неуспешной
- THEN уведомление уходит в личный чат агента
- AND в уведомлении есть идентификатор задачи и причина
- AND задача не выполняется повторно

### Requirement: Постоянные идентификаторы событий
События результата ДОЛЖНЫ иметь постоянные идентификаторы формата
`<taskId>:<type>:<version>`. Повтор события не создаёт повторное сообщение у получателя,
который поддерживает подтверждение.

#### Scenario: Повтор события
- GIVEN ассистент уже обработал событие результата
- WHEN агент присылает его повторно
- THEN ассистент подтверждает обработку
- AND не создаёт повторное сообщение

### Requirement: Ограниченные повторы доставки
Повтор доставки ДОЛЖЕН быть ограничен по числу и частоте. После исчерпания попыток
доставка помечается неуспешной, а владелец получает уведомление.

#### Scenario: Приёмник долго недоступен
- GIVEN все попытки доставки исчерпаны
- WHEN ошибка сохраняется
- THEN событие помечается неуспешным
- AND владелец получает уведомление с идентификатором задачи

#### Scenario: Ручной повтор
- GIVEN доставка помечена неуспешной
- WHEN владелец просит повторить доставку
- THEN событие ставится в очередь повторно с тем же идентификатором
- AND задача не выполняется заново

### Requirement: Ограничение дублей платформы фиксируется явно
Отчёт и документация ДОЛЖНЫ честно описывать, что при сбое непосредственно в момент
отправки в мессенджер абсолютное отсутствие дублей не гарантируется.

#### Scenario: Сбой между отправкой и подтверждением
- GIVEN сообщение отправлено в Telegram
- AND подтверждение отправки не сохранилось
- WHEN процесс восстанавливается и повторяет отправку
- THEN отчёт и документация не обещают отсутствия второго сообщения
- AND для событий ассистента дубль предотвращается постоянным идентификатором

### Requirement: Результат и ревизия различаются в отчёте
Отчёт ДОЛЖЕН показывать, является ли результат новой или доработанной версией, и сохранять
связь с исходной задачей.

#### Scenario: Доработка
- GIVEN владелец просит изменить раздел ранее выданного документа
- WHEN агент отправляет новый результат
- THEN в отчёте видно, что это версия 2 задачи с прежним корнем
- AND прежняя версия не удаляется сразу
