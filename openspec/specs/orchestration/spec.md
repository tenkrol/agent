# Спека домена orchestration

## ADDED Requirements

### Requirement: Оркестратор — единственный владелец жизненного цикла
Принятая задача ДОЛЖНА выполняться через один оркестратор: исполнение, проверка и
исправление. Адаптер входа (Telegram, HTTP-мост, расписание) не ведёт второй цикл
исполнения или исправления.

#### Scenario: Задача из бота
- GIVEN корректный запрос по действующему контракту
- WHEN задача принята
- THEN она выполняется зарегистрированным исполнителем один раз
- AND результат возвращается в исходный маршрут прежним контрактом.

#### Scenario: Неизвестный исполнитель
- GIVEN запрошен исполнитель, которого нет в реестре
- WHEN оркестратор выбирает исполнителя
- THEN возвращается понятная ошибка
- AND тихая подмена другим исполнителем не происходит.

### Requirement: Общая отмена
Потеря аренды ДОЛЖНА останавливать реальное исполнение через общий сигнал попытки и
НЕ ДОЛЖНА приводить к записи cancelled/failed или публикации результата старой попыткой.

#### Scenario: Heartbeat потерян
- GIVEN DSH выполняется под арендой SQLite
- WHEN heartbeat отрицателен и аренда перехвачена
- THEN runner получает abort
- AND старая попытка не пишет терминальный статус и не доставляет ответ
- AND новая попытка может продолжить задачу.

### Requirement: Остаточный бюджет
Бюджет ДОЛЖЕН учитывать расход проверяющей модели. Проверка ограничивается остатком
времени, а исчерпание бюджета после успешной проверки не даёт `done`.

#### Scenario: Бюджет исчерпан после проверки
- GIVEN лимит 100 токенов, исполнение и проверка израсходовали больше
- WHEN проверка успешна
- THEN итог не `done`
- AND причина отражает бюджет.

## ADDED Requirements

### Requirement: Быстрый ответ — часть жизненного цикла
Быстрый ответ ДОЛЖЕН проходить через оркестратор и не закрывать задачу самостоятельно.

#### Scenario: Быстрый ответ
- GIVEN задача решается быстрым слоем
- WHEN ответ получен
- THEN терминальный статус ставит оркестратор
- AND отмена и бюджет действуют так же, как для DSH.

## ADDED Requirements

### Requirement: Оркестратор владеет очередью и восстановлением
Очередь принятых задач, текущая попытка, восстановление из журнала и awaiting ДОЛЖНЫ
принадлежать `orchestration`. `AgentBot` не ДОЛЖЕН вести второй массив очереди или
собственные терминальные переходы.

#### Scenario: Восстановление после рестарта
- GIVEN в журнале есть queued и interrupted задачи
- WHEN сервис запускается
- THEN orchestration восстанавливает очередь в прежнем порядке
- AND interrupted не запускаются автоматически
- AND открытые вопросы восстанавливаются.

#### Scenario: Вопрос и ответ
- GIVEN задача ждёт ответа
- WHEN владелец отвечает
- THEN ответ продолжает ту же задачу через orchestration
- AND новый цикл очереди не создаётся.

### Requirement: Терминальные переходы — один выход
Терминальный статус ДОЛЖЕН писаться через `orchestration`; `AgentBot` только доставляет
сообщение. Повторная доставка результата не перезапускает вычисление.

#### Scenario: Доставка не удалась
- GIVEN результат готов, но доставка упала
- WHEN доставка повторяется
- THEN DSH не запускается снова
- AND повтор идёт с прежним eventId.

## ADDED Requirements

### Requirement: Безопасное восстановление SQLite
При старте без новых задач orchestration ДОЛЖЕН восстановить pending/running из SQLite,
дождаться истечения аренды и перезапустить выполнение; workers>1 отклоняется до изоляции
workspace/runner/progress.

#### Scenario: Рестарт до TTL
- GIVEN running-задача с арендой, сервис упал
- WHEN сервис поднялся до TTL и новых задач нет
- THEN после истечения аренды задача снова захватывается
- AND выполняется один раз.

## ADDED Requirements

### Requirement: Реестр исполнителей с метаданными
Реестр ДОЛЖЕН отдавать по каждому исполнителю id, capabilities, limits,
modelProfile, tools и status; метаданные доступны для API/диагностики.

#### Scenario: Диагностика
- GIVEN DSH-исполнитель зарегистрирован
- WHEN запрашивается describe()
- THEN видны его лимиты, профиль модели и инструменты.

## ADDED Requirements

### Requirement: Профили агентов
Оркестратор ДОЛЖЕН публиковать профиль модели/лимиты исполнителя в describe().

#### Scenario: describe
- GIVEN настроен профиль dsh
- WHEN вызывается describe()
- THEN profile виден в метаданных.

## ADDED Requirements

### Requirement: Выбор исполнителя по задаче
Оркестратор ДОЛЖЕН выбирать исполнителя через `selectExecutor`; при отсутствии
выбора используется dsh. Repair идёт тем же исполнителем.

#### Scenario: Файловая задача
- GIVEN зарегистрирован files
- WHEN selectExecutor выбирает files
- THEN execute и repair вызывают files.

## ADDED Requirements

### Requirement: Маршрутизация задач наблюдения
Задачи о состоянии хоста/сервисов ДОЛЖНЫ попадать в исполнителя monitor.

#### Scenario: Проверка сервера
- GIVEN зарегистрирован monitor
- WHEN задача просит проверить диск и память
- THEN selectExecutor выбирает monitor.

## ADDED Requirements

### Requirement: Маршрутизация личных задач
Личные задачи (память, предпочтения, напоминания) ДОЛЖНЫ попадать в personal.

#### Scenario: Вопрос о памяти
- GIVEN personal зарегистрирован
- WHEN задача спрашивает, что известно владельцу
- THEN выбирается personal.

## ADDED Requirements

### Requirement: Профиль не выдаётся за действующий без поддержки
Если DSH не умеет переключать модель на вызов, исполнитель ДОЛЖЕН показывать
`profileStatus: unsupported`, а не действующий профиль.

#### Scenario: describe
- GIVEN files/monitor/personal на общем headless runner
- WHEN вызывается describe()
- THEN profileStatus=unsupported виден в реестре.
