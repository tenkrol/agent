# Спека домена workflow

Правила самого процесса разработки: как оформляются изменения, как проверяется структура,
где живут секреты и на каком языке пишутся спеки.

## ADDED Requirements

### Requirement: Изменение оформляется папкой change
Любое изменение поведения ДОЛЖНО иметь папку `openspec/changes/PLA-<номер>/` (сквозной
номер по порядку) с `proposal.md`, `design.md`, `tasks.md` и дельтой-спекой в
`specs/<домен>/spec.md`.

#### Scenario: Новая возможность
- GIVEN в репозитории нет папки изменения для задачи
- WHEN агент или человек начинает менять поведение
- THEN сначала создаётся папка изменения со спекой
- AND код меняется только после одобрения спеки владельцем

#### Scenario: Правка без изменения поведения
- GIVEN изменение — опечатка или форматирование
- WHEN оно коммитится
- THEN в сообщении коммита стоит пометка «без change»
- AND папка изменения не создаётся

### Requirement: Структура проверяется автоматически
`bash tools/spec-check.sh` ДОЛЖЕН находить папки изменений без proposal, tasks или дельты,
имена не в формате `PLA-<номер>` и дельты без требований.

#### Scenario: Неполное изменение
- GIVEN в `changes/` лежит папка без `tasks.md`
- WHEN запускается `spec-check`
- THEN команда завершается с ненулевым кодом
- AND перечисляет, чего не хватает

### Requirement: Секреты не попадают в репозиторий
Значения ключей НЕ ДОЛЖНЫ попадать в репозиторий, в промпт задачи, в чат или в логи.

#### Scenario: Нужен ключ для работы
- GIVEN задаче нужен доступ к внешнему API
- WHEN составляется промпт
- THEN в промпте нет значений секретов
- AND ключ берётся из окружения процесса на сервере

### Requirement: Спеки и комментарии на русском
Требования, сценарии, документация и комментарии в коде пишутся по-русски, требования
формулируются через «ДОЛЖЕН» и сценарии GIVEN/WHEN/THEN.

#### Scenario: Новая спека
- GIVEN агент пишет дельту-спеку
- WHEN он формулирует требование
- THEN текст на русском, формат «ДОЛЖЕН» + сценарий GIVEN/WHEN/THEN

### Requirement: Работа завершается коммитом и пушем
Закрытое изменение ДОЛЖНО быть закоммичено и отправлено в `origin/main`. Неотправленный
коммит и незакоммиченные файлы считаются незавершённой работой: их не видят владелец,
другие сессии и другие машины.

#### Scenario: Сессия закрыла изменение
- GIVEN сессия влила дельту, обновила HANDOFF и закоммитила
- WHEN работа объявлена завершённой
- THEN коммит отправлен в `origin/main`
- AND `bash tools/git-check.sh` подтверждает: дерево чистое, всё отправлено

#### Scenario: Нет доступа к origin
- GIVEN пуш невозможен (нет сети или доступа)
- WHEN сессия завершает работу
- THEN она прямо сообщает об этом владельцу
- AND не оставляет это незамеченным

## ADDED Requirements

### Requirement: Крупное изменение — ветка и проверка
Изменение, меняющее жизненный цикл задач, ДОЛЖНО разрабатываться в отдельной ветке;
`main` обновляется после проверки. Прямой push в `main` для такого изменения не
допускается.

#### Scenario: Этап оркестратора
- GIVEN изменение затрагивает исполнение и отмену задач
- WHEN работа готова
- THEN код и спека лежат в ветке
- AND слияние выполняется после независимой проверки и прогона тестов.

## ADDED Requirements

### Requirement: Draft заявки
Система ДОЛЖНА из текста владельца создать draft-заявку с requestId, revision,
request/proposal/acceptance и manifest; manifest проверяется до записи.

#### Scenario: Невалидные компоненты
- GIVEN в компоненте нет specificationCommit
- WHEN создаётся draft
- THEN запись не выполняется
- AND возвращается понятная ошибка.

## ADDED Requirements

### Requirement: Реализация заявки в отдельной ветке
Система ДОЛЖНА по заявке запускать DSH в изолированном checkout компонента и
публиковать изменения в ветке `impl/<REQ>-<changeId>`, не трогая main.

#### Scenario: Успешная реализация
- GIVEN заявка с компонентными спеками
- WHEN запускается implement
- THEN DSH работает в каталоге компонента
- AND изменения уходят в ветку impl, main не меняется.

#### Scenario: Ошибка DSH
- GIVEN DSH завершился ошибкой
- WHEN implement завершается
- THEN ветка impl не публикуется.

## ADDED Requirements

### Requirement: Проверки перед публикацией реализации
Ветка `impl/<REQ>-<changeId>` ДОЛЖНА публиковаться только после успешных проверок
компонента; при падении выполняется ограниченный repair, иначе ветка не пушится.

#### Scenario: Проверки упали
- GIVEN тесты реализации не проходят
- WHEN repair не исправил
- THEN ветка impl не публикуется
- AND ошибка возвращается вызывающему.

## ADDED Requirements

### Requirement: Установка только после подтверждения и проверок
Установка реализации ДОЛЖНА требовать подтверждения владельца и зелёных проверок;
иначе merge/install не выполняются.

#### Scenario: Нет подтверждения
- GIVEN запрос без confirm
- WHEN вызывается deploy
- THEN установка не запускается.

#### Scenario: Красные проверки
- GIVEN проверки ветки не зелёные
- WHEN вызывается deploy
- THEN merge и install не выполняются.

## ADDED Requirements

### Requirement: Заявка и манифест
Доработка ДОЛЖНА иметь заявку с `manifest.json`: requestId, revision, компоненты,
changeId, base/specification SHA, зависимости и политики; манифест проверяется
валидатором до исполнения.

#### Scenario: Некорректный манифест
- GIVEN отсутствует specificationCommit
- WHEN манифест проверяется
- THEN проверка падает с понятной ошибкой
- AND задача не запускается.

### Requirement: Ветка → проверки → PR
Изменение кода ДОЛЖНО идти в ветке задачи, проходить проверки и PR; прямой push
доработки в main запрещён. Подтверждение относится к SHA спеки.

#### Scenario: Изменённая спека
- GIVEN спека принята на SHA A
- WHEN SHA меняется на B
- THEN прежнее подтверждение не действует автоматически
- AND нужна новая проверка/подтверждение.

## ADDED Requirements

### Requirement: Реализация только согласованной ревизии
DSH ДОЛЖЕН запускаться только для заявки с approval, совпадающим по revision и
точным SHA компонентных спецификаций; checkout выполняется на этом SHA.

#### Scenario: Черновик
- GIVEN заявка draft без approval
- WHEN вызывается implement
- THEN DSH не запускается.

#### Scenario: Спека изменилась
- GIVEN SHA спецификации изменён после approval
- WHEN вызывается implement
- THEN запуск отклоняется.

## ADDED Requirements

### Requirement: Публикуется проверенный результат слияния
В main ДОЛЖЕН попадать только commit, полученный слиянием проверенного implementation
SHA с актуальным main и прошедший проверки именно в этом результате.

#### Scenario: Проверки слияния красные
- GIVEN тесты integration checkout падают
- WHEN deploy завершается
- THEN main не меняется.

#### Scenario: Чужая ветка
- GIVEN branch не совпадает с веткой verified-результата
- WHEN вызывается deploy
- THEN выпуск отклоняется.

## ADDED Requirements

### Requirement: Почасовой подбор ready-заявок
Система ДОЛЖНА раз в час детерминированно находить approved/ready заявки и ставить
реализацию в очередь; повторный опрос не создаёт вторую попытку без retry.

#### Scenario: Повторный опрос
- GIVEN заявка уже в очереди/выполнена
- WHEN poller снова её видит
- THEN дубликат не создаётся.

### Requirement: Устойчивость операции
Операция реализации ДОЛЖНА использовать очередь, аренду и отмену; потеря аренды
останавливает реализацию.

#### Scenario: Отмена
- GIVEN реализация выполняется
- WHEN заявку отменяют
- THEN signal отменяется и статус не done.

## ADDED Requirements

### Requirement: Установка не выдаётся за merge
Deploy ДОЛЖЕН отдельно сообщать merged/checked/published SHA и installed.state;
неудачный healthcheck откатывается и не становится healthy.

#### Scenario: Healthcheck failed
- GIVEN install вернул healthy=false
- WHEN deploy завершается
- THEN rollback вызван
- AND состояние rolled_back, ok=false.

## ADDED Requirements

### Requirement: Ready-спецификация до согласования
Согласование ДОЛЖНО быть возможно только после DSH-исследования кода и готовой
спецификации с критериями; draft не согласуется.

#### Scenario: Draft approval
- GIVEN status draft
- WHEN вызывается approve
- THEN согласование отклоняется.

#### Scenario: Specify
- GIVEN draft с компонентами
- WHEN вызывается specify
- THEN DSH заполняет спеку в spec-ветке
- AND status становится ready с новыми SHA.

## ADDED Requirements

### Requirement: Контрольная строка `Acceptance E2E smoke` в README
`README.md` в корне репозитория ДОЛЖЕН содержать отдельную строку, начинающуюся с
`Acceptance E2E smoke`, чтобы результат сквозной приёмки REQ-0010 был проверяем по
документации и не терялся при правках.

#### Scenario: Строка присутствует
- GIVEN в README есть раздел «Тесты и разработка»
- WHEN реализация PLA-51 завершена и запускается `test/readme.test.mjs`
- THEN в README есть строка, начинающаяся с `Acceptance E2E smoke`
- AND тест наличия строки проходит.

#### Scenario: Строку удалили или переименовали
- GIVEN контрольная строка удалена, переименована или спрятана в середину другой строки
- WHEN запускается `test/readme.test.mjs`
- THEN тест падает с сообщением об отсутствии `Acceptance E2E smoke`
- AND приёмка PLA-51 не считается пройденной.

#### Scenario: Существующая отметка E5 не потеряна
- GIVEN в README уже есть строка `E5 implementation check`
- WHEN добавляется новая контрольная строка
- THEN строка E5 остаётся на месте
- AND оба теста `test/readme.test.mjs` проходят.

#### Scenario: Изменение не трогает код продукта
- GIVEN реализация PLA-51 завершена
- WHEN проверяется diff
- THEN изменены README, тесты и документы процесса
- AND код продукта, API, конфигурация, состояние и секреты не менялись.
