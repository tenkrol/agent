# Техническое решение

## Границы
```text
src/orchestration/
  index.mjs          # публичный интерфейс (пока реэкспорт)
  orchestrator.mjs   # цикл исполнение → проверка → исправление
  lifecycle.mjs      # стадии, разрешённые переходы, итоговый статус
  budget.mjs         # общий остаток токенов/шагов/времени
  registry.mjs       # реестр исполнителей и явная ошибка неизвестного
src/agents/dsh/
  index.mjs          # адаптер существующего runner.run
```
Оркестратор не импортирует Telegram, HTTP, GitHub и `core/bot.mjs`. Он получает
исполнителя из реестра и порт проверки; файлы, доставка, парковка вопроса и отчёт
остаются адаптеру входа.

## Контракт исполнителя
```js
executor.id
executor.capabilities
executor.execute({ task, sessionId, signal, id, tokenBudget, maxSteps, timeoutMs })
// -> результат существующего runner: ok, text, usage, aborted, timedOut, stepsExceeded...
```
`dsh` — первый зарегистрированный исполнитель. Неизвестный `executorId` — ошибка.

## Идентификаторы и снимок
`taskId` остаётся пользовательским; `attemptId` = `<taskId>-1`, исправление —
`<taskId>-fix-<n>`. Процедура и её лимиты фиксируются при принятии задачи (уже в журнале);
смена конфигурации не меняет принятую задачу. Существующая схема журнала не переписывается.

## Стадии и статусы
Внутренние: `queued → executing → verifying → repairing → done/partial/failed/cancelled/interrupted`.
Публичные статусы журнала не переименовываются. `classifyOutcome`:
- остановка сервиса + abort → `interrupted`, причина «перезапуск сервиса»;
- abort владельца → `cancelled`;
- timeout/budget/steps → `failed` с соответствующей причиной;
- `ok` и проверка не `passed` → `partial`;
- иначе `done`.
Доставка результата не входит в вычисление задачи: ошибка доставки не перезапускает DSH.

## Отмена и бюджет
Один `AbortController` создаётся в адаптере входа на попытку и передаётся оркестратору.
Исполнение, проверка и исправление получают этот сигнал; после каждой стадии проверяется
`aborted`. Исправление не начинается, если сигнал уже сработал.

Бюджет = минимум глобального лимита и лимита процедуры по токенам, шагам и времени.
`createBudget` считает остаток; исправление получает остаток, а не новый лимит. Неудачная
попытка тоже расходует бюджет. Если расход неизвестен, это отмечается явно и новые
бесплатные исправления не открываются. Точная остановка на последнем токене не обещается:
фиксируется измеренный перерасход и запрещается следующая стадия.

## Проверка
Порт проверки вызывает существующий `verifier.evaluate`; адаптер входа собирает файлы
до/после запуска и передаёт их. После отмены поздний ответ проверки не превращает исход в
успех. Стоимость проверяющей модели пока не возвращается портом — это известное ограничение
этапа, фиксируется в отчёте (бюджет проверки консервативно не увеличивается).

## Восстановление
Политика восстановления журнала не меняется: ожидающие задачи сохраняются, активная после
рестарта становится прерванной, недоставленный результат повторяется с прежним eventId.
Оркестратор не вводит второго писателя журнала.

## Влияние
- `src/core/bot.mjs`: конструктор получает оркестратор; `executeTask` делегирует цикл,
  сохраняет подготовку входа, парковку вопроса/вариантов, доставку и отчёт.
- `src/execution/dsh-task.mjs`: `timeoutMs` в `run` как per-run лимит.
- `src/agents/dsh`, `src/orchestration` — новые модули.
- Откат — предыдущий релиз/ветка; схема состояния не меняется.

## Альтернативы
- Оставить цикл в `bot.mjs` и добавить только отмену — не устраняет второго владельца.
- Ввести SQLite/несколько работников сразу — вне этапа 1, риск для работающего бота.
- Перенести проверку внутрь DSH — теряется независимость проверки.
