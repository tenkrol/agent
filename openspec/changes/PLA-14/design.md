# Техническое решение

## Как устроено сейчас
- Вход: `BotLinkServer` (`bridge-http.mjs`) принимает `POST /bridge` с `{task, source}`,
  проверяет bearer-токен и длину, зовёт `bot.submitBridgedTask`, отвечает `202 {taskId}`.
- Задача из моста выполняется как личная задача владельца: `chatId` = личный чат
  владельца, `variantsMode: 'never'`, `freshSession: true`. Вопрос задать нельзя, вариантов
  нет.
- Выход: `reportResult`/`parkForAnswer`/`parkForVariants` вызывают
  `mirrorResult` → `mirrorToAssistant` → `postOutbox` (`integrations/outbox.mjs`): один
  `POST /outbox` с `{text, title}`, текст обрезается до 3500 символов, ответ ассистента не
  анализируется (`ok`/`status`), повторов нет.
- Маршрут исходного разговора нигде не хранится: `chatId` задачи — это личный чат агента,
  а не разговор ассистента. Идентификатора события нет.
- Состояние задачи и факт доставки смешаны: `done` ставится до отправки, ошибка доставки
  только логируется, повторить отправку без повторного выполнения нельзя.
- Ревизий нет: владелец просит доработать — это новая независимая задача.

## Предлагаемое решение

### Модули
```
src/bot-link/
  protocol.mjs     разбор и валидация запросов контракта v2
  bridge-http.mjs  маршруты /v1/* и прежний /bridge (совместимость)
  route.mjs        маршрут ответа: проверка и хранение
  events.mjs       сборка событий доставки с постоянным eventId
  deliver.mjs      воркер доставки: выборка, повтор, учёт ack
  mirror.mjs       прежнее зеркалирование (совместимость, тонкая обёртка)
src/storage/
  deliveries.mjs   журнал событий доставки и подтверждений
  tasks.mjs        поля route, version, rootTaskId, revisionOf, resultSummary
src/integrations/
  outbox.mjs       postAgentEvent (контракт v2) + postOutbox (прежний)
```

### Входящие маршруты
- `GET /v1/health`, `GET /v1/capabilities` — без токена только health, как сейчас.
- `POST /v1/tasks` — валидация `contract: 2`, `task`, `requestId`, `route`, вложений;
  создание задачи через `accept()` из PLA-13; ответ `202` после сохранения.
- `GET /v1/tasks/:id` — состояние из журнала: `execution`, `delivery`, `question`,
  `result`, `version`, `rootTaskId`, `revisionOf`.
- `POST /v1/tasks/:id/reply` — ответ на вопрос: продолжение той же задачи с сохранённой
  сессией (как `continueTask`), `202`.
- `POST /v1/tasks/:id/cancel` — остановка выполнения/ожидания, идемпотентно.
- `POST /bridge` — прежний запрос; маппится во внутреннюю задачу без `route` с
  `source: legacy`, ответ прежний.

Авторизация: тот же bearer-токен, `timingSafeEqual`; лимиты тела и длины — из конфига.
`route` проверяется по настройке ассистента (`BRIDGE_ROUTE_BOT_ID`, `BRIDGE_ROUTE_CHAT_ID`
или список разрешённых); чужой маршрут — `400`.

### Маршрут и диалог
- Запись задачи получает `route` (платформа, бот, чат, тред, сообщение) и
  `source: assistant`. Все вопросы, варианты, результат и уведомление об отмене уходят по
  этому маршруту; личный чат агента остаётся для личных задач.
- Для задачи с маршрутом `variantsMode` больше не форсируется в `never`: уточняющий вопрос
  и варианты разрешены, сессия сохраняется для продолжения. План на утверждение по-прежнему
  не показывается (утверждать некому), это не мешает вопросам.
- Вопрос доставляется событием `question`; ответ приходит `POST /v1/tasks/:id/reply` и
  будит ту же задачу (тот же `id`, тот же `sessionId`), а не создаёт новую.
- Если `route` нет (личная задача), поведение прежнее: вопрос в чате агента, ответ
  сообщением.

### Доставка как отдельное состояние
- `src/storage/deliveries.mjs` — append-only `deliveries.jsonl`:
  `{ version, eventId, taskId, type, route, payload, state, attempts, nextAttemptAt,
  createdAt, sentAt, ackedAt, lastError }`. Последняя строка для `eventId` побеждает.
- Состояния: `pending → sending → sent → acked | failed`. `sent` — передано, но ack нет;
  `acked` — ассистент подтвердил обработку; `failed` — исчерпаны попытки.
- `eventId` постоянный: `<taskId>:<type>:<version>:<sequence>`; повтор всегда с тем же
  идентификатором.
- `deliver.mjs` — воркер (тик `DELIVERY_TICK_MS`): выбирает `pending` с
  `nextAttemptAt <= now`, отправляет через `postAgentEvent`, обновляет запись. Расписание
  повторов `DELIVERY_RETRY_MS` (по умолчанию 60 с, 5 мин, 15 мин, 1 ч, 6 ч), не больше
  `DELIVERY_MAX_ATTEMPTS` (по умолчанию 8). Ошибка `4xx` — терминальная (`failed`).
- Перед отправкой события пишется действие в журнал PLA-13 (`started`), после ответа —
  `confirmed` с `eventId` и `processed`; так повтор после сбоя процесса не теряет факт
  отправки.
- Выполнение и доставка независимы: смена `delivery.state` никогда не меняет `execution`;
  повтор доставки не запускает исполнителя. При старте воркер подхватывает незавершённые
  доставки.
- Прямая отправка в чат агента (Telegram) тоже учитывается в журнале действий и получает
  ограниченный повтор; абсолютной гарантии отсутствия дублей нет — если процесс упал между
  `sendMessage` и подтверждением, повтор может создать второе сообщение. Ограничение
  фиксируется в отчёте и документации, как требует проект требований.
- Ручной повтор: `/deliver <taskId>` — поставить события задачи в очередь повторно (для
  разбора инцидентов).

### Ревизии результата
- `POST /v1/tasks` с `revisionOf`:
  - проверяется, что прошлая задача существует и её результат доступен;
  - создаётся задача с `rootTaskId` (корень), `revisionOf`, `version = прошлая + 1`;
  - в промпт добавляется прошлый результат (текст, список файлов, пути) и просьба изменить
    только запрошенное;
  - файлы прошлой версии берутся из рабочей папки; если их уже нет по сроку хранения —
    задача всё равно создаётся, а в отчёте явно сказано, что прошлый файл недоступен.
- `GET /v1/tasks/:id` показывает версию и связь; прежняя версия остаётся в журнале и
  доступна по `id` согласно `OUTPUT_RETENTION_DAYS`.

### Совместимость и порядок выката
1. Чат-бот первым получает приём событий v2 с дедупликацией и `ack` (своё изменение в
   `tenkrol/assistant`); старый `/outbox` он тоже принимает.
2. Агент выкатывается с `CONTRACT_V2=true`: `/v1/*` и события работают, `/bridge` и
   `/outbox`-текст сохраняются.
3. Старый ассистент: задача через `/bridge` без `route`, результат текстом через
   `/outbox`; событие содержит поле `text`, поэтому доставка не ломается.
4. Откат агента — симлинк на предыдущий релиз; контракт v1 остаётся в коде до отдельного
   решения об удалении.

### Конфиг
`CONTRACT_V2` (true), `BRIDGE_ROUTE_BOT_ID`, `BRIDGE_ROUTE_CHAT_ID`,
`DELIVERY_TICK_MS` (30 000), `DELIVERY_RETRY_MS` (список), `DELIVERY_MAX_ATTEMPTS` (8),
`DELIVERY_TEXT_CHARS` (3500). Все значения — в `config`, `.env.example`, README.

### Миграция и откат
- Старые записи журнала не имеют `route` — считаются личными задачами; `version` = 1,
  `rootTaskId` = `id`.
- `deliveries.jsonl` создаётся пустым; доставки, начатые старым кодом, неизвестны — при
  первом запуске новых незавершённых нет.
- Откат: предыдущий релиз агента; события, отправленные v2-агентом, старый ассистент
  получит как обычный текст (поле `text` есть). Задачи, созданные через `/v1/*`, старому
  коду видны как обычные записи журнала.

## Влияние
- Меняются `src/bot-link/*`, `src/integrations/outbox.mjs`, `src/storage/` (журнал доставок,
  поля задачи), `src/core/bot.mjs` (воркер, маршрут, ревизии, вопросы из моста),
  `src/config/`, тесты, README и `.env.example`.
- Ассистент обязан обновиться, чтобы получить адресность, вопросы и дедупликацию; без его
  обновления работает прежний сценарий (личный чат + текст), это проверяется тестом
  совместимости.
- Риск: ошибка маршрута отправит результат не в тот чат — закрывается проверкой `route` по
  настройке и тестами на чужой/пустой маршрут.
- Риск: повтор события после `ack` без дедупликации у ассистента — закрывается постоянным
  `eventId` и требованием к ассистенту.

## Альтернативы
- Оставить один `POST /bridge` и добавить поля — не даёт версионирования и состояния;
  отвергнуто.
- Отдельная очередь сообщений (Redis/брокер) — ноль зависимостей в рантайме и лишняя
  инфраструктура; отвергнуто в пользу журнала на диске.
- Доставлять результат только через личный чат агента и не возвращать в разговор —
  противоречит требованию «возврат в исходный разговор»; отвергнуто.
- Опрашивать ассистента (`GET /outbox`) — на его стороне нет очереди, лишний цикл;
  отвергнуто в пользу push с `ack`.
