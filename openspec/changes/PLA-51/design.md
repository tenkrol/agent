# Техническое решение

## Домен и границы

Требование относится к домену `workflow`: это правило процесса разработки и
документации, как и контрольная отметка E5 в PLA-32. Домен `acceptance` описывает
приёмку этапов E0–E11 с доказательствами и здесь не меняется. Границы изменения —
`README.md`, `test/readme.test.mjs` и документы процесса; на этапе спеки `main` и код
продукта не меняются.

## Как устроено сейчас

- `README.md` — пользовательская документация компонента. В разделе «Тесты и
  разработка» уже есть контрольная отметка E5 (`E5 implementation check`) и указание,
  что её проверяет `test/readme.test.mjs`.
- `test/readme.test.mjs` читает `README.md` из корня репозитория и требует совпадение
  `/^E5 implementation check/m`. Файл попадает в общий прогон `test/*.test.mjs`.
- README не участвует в рантайме. В релиз он попадает как документация (юниты
  ссылаются на `file:/opt/agent/README.md`).
- Отдельного E2E/acceptance-раннера в репозитории нет: приёмка ведётся в
  `docs/acceptance/` и в заявках, а README служит видимой контрольной отметкой.

## Контракты между компонентами

1. **README ↔ человек/приёмка.** Отдельная строка, начинающаяся с
   `Acceptance E2E smoke`, — стабильный маркер результата REQ-0010. Пояснение после
   тире допустимо, но не обязательно; маркером считается начало строки.
2. **README ↔ `test/readme.test.mjs`.** Тест читает `README.md` из корня репозитория
   и проверяет regex `/^Acceptance E2E smoke/m`. Это единственный автоматический
   контракт изменения; он не зависит от сети, конфигурации и состояния.
3. **`test/readme.test.mjs` ↔ общий прогон тестов.** Новый тест лежит в существующем
   файле, поэтому автоматически выполняется командой
   `node --test --test-force-exit test/*.test.mjs`; новых зависимостей нет.
4. **С API, конфигурацией, storage и deploy-скриптами контрактов нет.** Строка не
   читается рантаймом и не влияет на поведение агента.

## Предлагаемое решение

1. В `README.md` после абзаца с `E5 implementation check` добавить абзац:
   `Acceptance E2E smoke — контрольная строка README для заявки REQ-0010 (change PLA-51);`
   `её наличие проверяет test/readme.test.mjs.`
2. В `test/readme.test.mjs` добавить второй тест по образцу существующего: прочитать
   README и выполнить `assert.match(readme, /^Acceptance E2E smoke/m)`.
3. Существующий тест E5 не менять. Новых файлов и зависимостей не добавлять.

Почему так: это минимальное изменение, оно повторяет уже проверенный шаблон PLA-32,
не требует исполняемого E2E-раннера и оставляет контрольную строку видимой в
документации. Размещение рядом с E5 сохраняет все контрольные отметки в одном месте.

## Совместимость

- README — Markdown; добавление абзаца не ломает команды, ссылки и существующие
  парсеры. Строка E5 остаётся на месте.
- Число тестов увеличивается на один; существующие тесты не зависят от отсутствия
  новой строки.
- API, конфигурация, формат состояния и секреты не меняются, поэтому обратная
  совместимость продукта сохраняется.

## Миграции

Не требуются: нет схем, форматов, состояния и данных, которые нужно переносить.
Откат — удалить добавленный абзац и новый тест либо откатить коммит целиком.

## Базовая линия проверок

На 2026-10-18 21:35 UTC (00:35 `Europe/Moscow`) полный прогон `test/*.test.mjs` даёт
два падения вне PLA-51: `test/plan.test.mjs` («an unattended task gets a plan without
waiting for approval») и `test/quick.test.mjs` («the bot answers a trivial request
itself and records the spend»). Оба падают на границе суток UTC/`Europe/Moscow`:
запись и проверка расхода попадают в разные календарные дни. Это существующая
проблема тестов, не связанная с README; в PLA-51 её не исправляем. Перед реализацией
нужно повторить прогон на актуальном времени, убедиться, что других падений нет, а
после изменения — что список не вырос.

## План выпуска

1. Владелец одобряет спеку и отвечает на `questions.md` (или соглашается с
   рекомендациями).
2. Спека лежит в ветке `spec/REQ-0010-PLA-51`; реализация — в отдельной ветке
   `impl/REQ-0010-PLA-51`. `main` до проверок не меняется, код продукта на этапе
   подготовки спеки не затрагивается.
3. Проверки: `bash tools/spec-check.sh`, `node --test --test-force-exit
   test/readme.test.mjs`, затем полный прогон
   `node --test --test-force-exit test/*.test.mjs`.
4. Коммит и пуш ветки, просмотр diff; merge в `main` — после подтверждения владельца
   по общему процессу (PLA-31/PLA-40). Для документационного изменения установка на
   сервер не обязательна; штатный `deploy/install-remote.sh` при необходимости
   положит README в очередной релиз.
5. Обновить `HANDOFF.md`, влить дельту в `openspec/specs/workflow/spec.md`, перенести
   папку в `changes/archive/PLA-51/`, выполнить `bash tools/git-check.sh`.

## Альтернативы

- **Отдельный E2E-скрипт или CI-джоба.** Отвергнуто: требование просит строку в
  README, а не новый раннер; это расширило бы границы изменения.
- **Хранить отметку только в `docs/acceptance/`.** Отвергнуто: владелец явно просит
  README.
- **Не добавлять тест.** Отвергнуто: без стража строку легко потерять; прецедент —
  E5/PLA-32, где такая проверка уже есть.

## Влияние и откат

Изменение документационное: приложение, API и конфигурация не затрагиваются.
Риск — случайное удаление строки при будущих правках README; его закрывает тест.
Откат безопасен и не требует миграций или перезапуска сервиса.
