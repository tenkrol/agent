# Техническое решение

## Как устроено сейчас
- `src/storage/memory.mjs`: `memory.json` с `{version: 1, facts: [{id, text, createdAt,
  source}]}`; предел 120 фактов по 300 символов; `add`, `forget`, `clear`, `render`
  (в промпт уходит весь список до 3000 символов), `ingest` фактов из `memory.md`.
- **Версия файла сейчас не проверяется**: `load()` разбирает JSON и берёт `facts`, не
  глядя на `version`, а `save()` всегда пишет `version: 1`. Поэтому миграция и откат
  должны быть описаны явно, а не полагаться на то, что старый код «сам отложит» новый файл.
- `execution/prompt.mjs` безусловно вставляет `memory.render()` в текст задачи.
- Команды: `/memory` (список), `/remember <текст>`, `/forget <номер|id|фрагмент>`.
- Секреты: значения не должны попадать в промпт/логи; сейчас есть только редактирование
  логов (`ops/logger.mjs`), проверок в памяти, показе и отчёте нет.

## Предлагаемое решение

### Схема памяти версии 2
```json
{
  "version": 2,
  "facts": [
    {
      "id": "f...",
      "text": "часовой пояс владельца — Europe/Moscow",
      "kind": "preference",
      "subject": "timezone",
      "scope": { "type": "global", "value": null },
      "source": { "type": "owner", "ref": "message:433296567:12345" },
      "createdAt": 1760000000000,
      "validFrom": 1760000000000,
      "validUntil": null,
      "status": "active",
      "supersedes": "f-old",
      "supersededBy": null
    }
  ]
}
```
- `kind`: `preference` (постоянное предпочтение), `temporary` (временное сведение с
  `validUntil`), `task` (контекст задачи; `scope.type = "task"`, `scope.value = taskId`).
- `source.type`: `owner` (владелец явно сообщил агенту), `agent` (агент вывел из своей
  работы). Факты ассистента в `memory.json` не сохраняются и потому источника
  `assistant` в хранилище нет.
- `scope.type`: `global`, `chat`, `task`.
- `status`: `active`, `superseded`, `expired`.
- Замена: новый факт с тем же `subject` + `scope` в статусе `active` переводит прежний в
  `superseded` и связывает `supersedes`/`supersededBy`. Прежний факт остаётся в истории.
- `validUntil` в прошлом → `expired` при загрузке/выборке; в промпт не попадает, в истории
  виден.
- Пределы: `MEMORY_MAX_FACTS` активных фактов (по умолчанию 120), 300 символов на факт
  (как раньше), история — до `MEMORY_HISTORY_MAX` (500), обрезка старых записей по времени.

### Владельцы данных
Явно различаем три вещи:

| Что | Кто хранит | Где | Срок |
|---|---|---|---|
| (а) рабочий контекст задачи | агент | `memory.json`, `kind: task`, `scope: task` | до закрытия задачи + `MEMORY_TASK_RETENTION_DAYS` |
| (б) предпочтения, которые владелец явно сообщил агенту для его работы | агент | `memory.json`, `kind: preference` или `temporary`, `scope: global/chat` | по `validUntil` или бессрочно |
| (в) личные факты ассистента | ассистент | вне агента; в задаче — только `context.facts` | на время задачи |

- Агент НЕ сохраняет личные факты, переданные ассистентом: они приходят в запросе задачи
  (`context.facts`) и используются только для этой задачи, после завершения не остаются ни
  в `memory.json`, ни в другой задаче.
- Предпочтение, которое владелец явно сообщил именно агенту для его работы, агент хранит
  сам (пункт «б»); это не личные факты ассистента.
- Рабочий факт, который агент хочет сохранить навсегда, уходит событием
  `memory_proposal`. Решение о долговременной записи личных фактов принимает ассистент;
  агент не записывает личную память молча.
- Если ассистент недоступен, предложение остаётся в очереди доставки (PLA-14) и
  повторяется; **оно не применяется молча**: до подтверждения ассистента факт живёт только
  в текущей задаче и не попадает в `memory.json`.
- `memory.md` из рабочей папки остаётся источником рабочих фактов агента (пункт «б»), но
  строка может содержать `subject`: `- [timezone] Europe/Moscow`; такая запись заменяет
  прежнюю с тем же `subject`. Без `subject` — обычное добавление. Личные факты ассистента
  через `memory.md` не сохраняются: для них путь один — `memory_proposal`.

### Выбор памяти для задачи
`memory.renderForTask({ text, scope, budget = config.memory.contextChars })`:
- берёт только `active` и неистёкшие факты;
- `scope.global` и `scope.chat` (этот чат), `scope.task` — только для своей задачи;
- отбирает по простому соответствию теме задачи (совпадение значимых слов) и свежести,
  затем добирает до бюджета; задача без темы получает только глобальные предпочтения;
- жёсткий предел `MEMORY_CONTEXT_CHARS` (по умолчанию 1500) — меньше прежних 3000:
  контекст задачи и так дорог, а лишние факты ухудшают результат;
- контекст задачи (`kind: task`) удаляется при закрытии задачи с учётом
  `MEMORY_TASK_RETENTION_DAYS`.

### Исправление устаревшего факта
- Владелец явно сообщает новое значение: команда `/memory set <subject> <текст>` или
  `memory.md` со `subject`, либо ассистент присылает факт с `subject` через согласованный
  интерфейс.
- Новая запись становится `active`, прежняя — `superseded`; в промпт попадает только
  активная; `/memory history <subject>` показывает обе с датами и источником.
- Удаление (`/forget`) остаётся, но не является способом «исправления»: история сохраняется
  до `/memory purge` (явная очистка, с подтверждением).

### Защита от секретов
Решение: guard живёт в домене `secrets` (`src/secrets/guard.mjs`), потому что это работа со
значениями секретов, а не с эксплуатацией или логгером.

- Guard — фабрика `createSecretGuard({ values })` в `src/secrets/guard.mjs`, возвращающая
  связанный порт `{ contains(text), redact(text), namesIn(text) }`. Значения получает
  только точка сборки (`src/index.mjs`) из `config` (`secretsOf`); домены получают уже
  связанный порт и не видят значений. Сам guard не читает окружение и файлы, не зависит от
  других доменов и не знает, откуда пришли значения.
- Архитектурное правило «Секреты — отдельный домен» меняется: `storage`, `execution` и
  `core` МОГУТ получать связанный guard-порт (только проверка/вырезание), но НЕ получают
  доступ к значениям секретов, шифртексту и `process.env`. Значения передаются только в
  точку сборки; `secrets` остаётся фундаментом и не зависит ни от одного домена.
- Память:
  - `add`/`apply` отклоняет факт, содержащий значение секрета (в лог — только имя ключа);
  - `/memory` и `/memory history` фильтруют/вырезают секреты даже из фактов, попавших в
    файл до обновления; при вырезании показывается пометка без значения;
  - при миграции все старые факты проходят скан `MEMORY_SECRET_SCAN`: найденные **не
    переносятся** (их значение не остаётся в файле), в историю попадает только пометка
    «факт содержал секрет» без текста.
- Промпт: перед сборкой проверяется; при утечке — факт исключается и пишется
  предупреждение.
- Отчёт: перед отправкой текст и имена файлов проверяются; найденное значение вырезается,
  владельцу уходит предупреждение «в отчёте был секрет, вырезан».
- Журнал памяти и логи: значения не пишутся; логгер уже редактирует известные секреты.

### Контракт с ассистентом (дополнение к PLA-14)
- `POST /v1/tasks` может содержать `context.facts` — **массив объектов**
  `{ "text": "…", "subject": "timezone", "validUntil": 1760000000000 }`
  (`subject` и `validUntil` необязательны). Агент проверяет: не больше 50 фактов, текст
  не длиннее 300 символов, `subject` не длиннее 60, `validUntil` — корректная дата;
  невалидный элемент — `400`. Факты используются только для этой задачи и не сохраняются.
- Событие `memory_proposal` — **service-событие**: `{ type: "memory_proposal",
  proposal: { text, subject?, kind, scope } }`, без полей `text`/`title` пользовательского
  сообщения. Оно не создаёт сообщение пользователю (ассистент не показывает его в чате),
  доставляется с постоянным `eventId` формата `<taskId>:memory_proposal:<версия>` и
  подтверждением обработки; отправляется только при `capabilities.serviceEvents: true`.
  При недоступности ассистента (если поддержка объявлена) событие ждёт в очереди доставки.
  Решение о долговременной записи принимает ассистент; агент не применяет своё предложение
  локально.
- Формат полей — в `openspec/changes/PLA-14/specs/bot-link/contract.md` (после архивации
  PLA-14 — `openspec/specs/bot-link/contract.md`). В PLA-17 дельта bot-link ссылается на
  контракт и уточняет service-семантику; правка самого contract.md — задача PLA-14
  (синхронизировать формат `context.facts` и тип `memory_proposal`).
- `GET /v1/memory/context?text=…` не вводится: отбор делает ассистент, агенту достаточно
  `context.facts`.

### Команды
- `/memory` — активная память по видам и областям, с датами и источником; секреты
  вырезаны;
- `/memory history [subject]` — история, включая заменённые и истёкшие; секреты вырезаны;
- `/memory set <subject> <текст>` — явное исправление (замена);
- `/remember [--until YYYY-MM-DD] [--kind temporary] <текст>` — добавление;
- `/forget <номер|id|фрагмент>` — забыть факт (история остаётся);
- `/memory purge` — полная очистка с подтверждением.

### Настройки
`config.memory`:

| Ключ | По умолчанию | Границы | Назначение |
|---|---|---|---|
| `MEMORY_CONTEXT_CHARS` | 1500 | 200–8000 | бюджет памяти в промпте |
| `MEMORY_HISTORY_MAX` | 500 | 50–5000 | предел истории (заменённые/истёкшие) |
| `MEMORY_TASK_RETENTION_DAYS` | 7 | 0–365 | срок хранения контекста закрытой задачи |
| `MEMORY_MAX_FACTS` | 120 | 10–1000 | предел активных фактов |
| `MEMORY_SECRET_SCAN` | true | boolean | скан старых фактов при миграции; показ памяти фильтрует всегда, `false` только для отладки и не снимает запрет на запись, промпт и отчёт |

Все ключи — в `config`, `.env.example` и README; неверное значение — ошибка при старте с
именем переменной.

### Миграция и откат
Новый `MemoryStore.load()` явно проверяет `version`:
- файла нет → пустая память, версия 2 при первой записи;
- `version: 2` → обычное чтение (незнакомые поля игнорируются, известные валидируются);
- `version: 1` (или поле отсутствует — так писал старый код) → миграция:
  1. скопировать текущий файл в `memory.json.v1.bak` (перезаписывается только при новой
     миграции);
  2. перенести факты в схему v2 (вид `preference`, область `global`, статус `active`,
     `subject: null`, источник `owner` или `agent` по прежнему полю);
  3. прогнать скан `MEMORY_SECRET_SCAN`: факты с секретом не переносятся, в историю
     добавляется пометка без значения;
  4. **сразу записать файл как `version: 2`** атомарно (`writeAtomic`); если запись не
     удалась — ошибка в лог, исходный v1-файл и `.v1.bak` на месте, миграция повторится при
     следующем старте;
- незнакомая/более новая версия → как в `StateStore`: копия
  `memory.json.corrupt-<дата>` через `quarantineCorrupt` и старт с пустой памятью; исходный
  файл не подменяется до первой записи;
- битый JSON → та же карантинная копия и пустой старт.

Откат:
- старый код версию не проверяет и при `/remember`/`ingest` перезапишет файл как
  `version: 1`, потеряв новые поля. Поэтому откат — **предыдущий релиз + восстановление
  `memory.json.v1.bak`** до запуска старого кода (файл кладётся на место `memory.json`).
- Это проверяется тестом: миграция → откат → старый код видит прежние факты.
- `memory.json` остаётся совместимым по расположению и правам (600).

## Влияние
- Меняются `src/storage/memory.mjs`, `src/execution/prompt.mjs`, `src/core/bot.mjs`
  (команды, показ памяти, проверка отчёта), новый `src/secrets/guard.mjs`,
  `src/bot-link` (контекст и service-событие), `src/config/`, `src/index.mjs` (сборка
  guard-порта), тесты, README.
- Промпт становится короче: меньше токенов на задачу, но выше требования к отбору —
  закрывается тестами релевантности.
- Риск: потеря фактов при миграции — закрывается `.v1.bak`, немедленной записью v2 и тестом
  миграции.
- Риск: секрет уже был в памяти до обновления — миграционный скан его не переносит, а показ
  памяти фильтрует; закрывается тестами.
- Риск: ассистент недоступен — предложение ждёт в очереди доставки, но не применяется
  молча; закрывается тестом.

## Альтернативы
- Оставить плоский список и добавить только `validUntil` — не решает владение, историю и
  исправление; отвергнуто.
- Векторный поиск по памяти — внешние зависимости и непрозрачность; отвергнуто.
- Хранить личные факты в агенте и синхронизировать с ассистентом — два владельца и
  конфликты; отвергнуто в пользу «ассистент владеет, агент использует на задачу».
- Автоматически заменять факты моделью — непредсказуемо и дорого; отвергнуто в пользу
  явного `subject` и команд.
- Guard в `ops` (рядом с логгером) — тогда `storage`/`execution`/`core` зависят от
  эксплуатационного домена, а работа со значениями секретов размазывается; отвергнуто в
  пользу чистого guard-порта в `secrets` с явным архитектурным исключением.
