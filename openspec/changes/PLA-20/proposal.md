# Этап 2: транзакционная очередь, аренды и восстановление

Основание: архитектура агентной системы, этап 2. Номер PLA-20: активных изменений нет,
архив заканчивается PLA-19.

## Зачем
Сейчас очередь живёт в памяти одного процесса, а журнал — append-only JSONL без
межпроцессной блокировки. Два исполнителя могут взять одну задачу, результат устаревшей
попытки нельзя отличить от актуального, а после падения работника нет аренды для
восстановления.

## Что меняется
- Транзакционная очередь на встроенном `node:sqlite` (проверено на сервере: Node 22.23.3,
  `node:sqlite` доступен; experimental — решение оформляется ADR и флагом).
- Аренда задачи: `leaseOwner`, `leaseUntil`, `generation`; захват только одной попыткой.
- Heartbeat и восстановление после потери работника; устаревшая попытка не может
  завершить задачу.
- Идемпотентная постановка по `requestId`; журнал побочных действий сохраняется.
- Ограничения параллельности по серверу, репозиторию и типу агента — в следующих шагах.

## Не входит
GitHub-конвейер, почасовой подбор, YandexGPT, перенос памяти, остальные агенты,
автоматический выпуск.

## Как проверяем
Тесты очереди: два претендента — один захват; heartbeat продлевает аренду; истёкшая
аренда восстанавливается; завершение с устаревшим `generation` отвергается; повторная
постановка возвращает ту же задачу. Миграция с журнала — отдельным шагом с бэкапом и
откатом; production не переключается до зелёных тестов и проверки.
