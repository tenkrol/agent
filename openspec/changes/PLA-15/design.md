# Техническое решение

## Как устроено сейчас
- `executeTask` (`src/core/bot.mjs`) после `runner.run` считает успех по `result.ok` и
  `exitCode`: разбирает ответ (`parseReply`), собирает файлы (`collectOutputs`), ставит
  `done`, отправляет текст и файлы. Ни одна проверка содержимого не выполняется.
- `delivery/report.mjs` собирает заголовок, тело, диагностику и подпись; поля «проверено»
  нет.
- `execution/dsh-task.mjs` — запуск DSH в cgroup с таймаутом; `execution/quick.mjs` — быстрый
  слой; `tools/` умеет извлекать текст из DOCX/XLSX/PDF и распознавать изображения, но не
  проверять результат.
- LibreOffice и venv (python-docx, openpyxl, python-pptx) на сервере есть; офисные проверки
  можно выполнять локально.

## Предлагаемое решение

### Новый домен verification
```
src/verification/
  criteria.mjs    вывод проверяемых критериев из запроса и типа результата
  index.mjs       оркестрация проверки: verify({ criteria, files, ports }) → результат
  document.mjs    проверка документа
  spreadsheet.mjs проверка таблицы
  code.mjs        проверка изменения кода
  research.mjs    проверка исследования
```
Домен не импортирует другие домены: ядро передаёт ему критерии, файлы и порты. Порты
объявляются как интерфейсы и реализуются в своих доменах:
- `ports.inspectDocument(path)` → `{ opens, text, sections, pages, renderTo(path) }`
  (реализация — `tools`);
- `ports.inspectSpreadsheet(path)` → `{ opens, sheets, values, formulas, errors, recalc() }`
  (реализация — `tools`);
- `ports.runCodeChecks({ cwd, commands, timeoutMs })` → `{ checks: [{ command, exitCode,
  stdout, stderr }] }` (реализация — `execution`, процессы в cgroup);
- `ports.askModel(prompt)` → текст (реализация — `integrations`, для критериев и
  исследования);
- `ports.now()`.
Направление зависимостей не нарушается: `core` вызывает `verification` и передаёт порты,
реализованные в `tools`/`execution`/`integrations` на сборке.

### Критерии результата
`criteria.mjs` получает формулировку владельца, тип результата и (если есть) план; выводит
`[{ id, text, kind, required, source }]`:
- `kind`: `format`, `sections`, `sources`, `data`, `computation`, `checks`, `other`;
- `required`: обязательные (по умолчанию) и дополнительные;
- `source` — фраза владельца, из которой критерий выведен, либо «минимальная проверка типа».
Минимальные проверки типов — из таблицы требований (документ открывается и содержит
требуемые разделы; таблица открывается, данные на месте, формулы пересчитаны; код —
подходящие проверки выполнены; исследование — выводы связаны с источниками, предположения
отделены).
Критерии не расширяют объём: `criteria.mjs` не добавляет требования, которых нет в
запросе или в минимальной таблице. Существенная неоднозначность (неясно, какой формат,
какие разделы, обязателен ли файл) — один вопрос владельцу через существующий протокол
`ВОПРОС:`; задача паркуется, выполнение не начинается.
Критерии сохраняются в записи задачи (`criteria`), попадают в промпт исполнителя
(`execution/prompt.mjs`) и в результат проверки.

### Проверка по типам
- **Документ**: открывается (ZIP/XML для DOCX, LibreOffice для ODT/PDF); требуемые разделы
  находятся в тексте; при значимых требованиях к оформлению — рендер в PDF/PNG и проверка
  отображения (порт `renderTo` + vision через `askModel`; если vision недоступен —
  `unavailable`).
- **Таблица**: открывается; листы/данные на месте; формулы пересчитаны LibreOffice
  (`recalc()`), значения сравнены с ожидаемыми; ошибки `#REF!`, `#VALUE!`, `#DIV/0!` —
  провал; при требованиях к формату проверяется отображение.
- **Код**: критерии `checks` превращаются в команды (тесты, линтер, сборка) и запускаются
  портом `execution` в cgroup с таймаутом; фиксируются команды, коды возврата, хвосты
  вывода; проверки, которые нельзя выполнить, — `unavailable`, а не «успех».
- **Исследование**: в ответе есть раздел источников; выводы связаны с источниками
  (модель-проверяющий с портом `askModel` и списком источников); предположения отделены от
  подтверждённых сведений; отсутствие источников — провал, если они требовались.

Результат проверки:
```json
{
  "status": "passed | failed | partial | unavailable | not_required",
  "criteria": [{ "id": "c1", "status": "passed|failed|unavailable|skipped", "evidence": "...",
                 "notes": "..." }],
  "attempts": 1,
  "checkedAt": 1760000000000,
  "limitations": ["что именно не удалось проверить"]
}
```
`status` вычисляется по обязательным критериям: все прошли — `passed`; часть не прошла или
недоступна — `partial`; ни один обязательный не проверен — `unavailable`; проверки не
требуются — `not_required`.

### Оркестрация в core
1. После подготовки задачи (до запуска) — критерии; при вопросе задача паркуется.
2. После успешного `runner.run` — переход `running → verifying`, вызов
   `verification.verify`.
3. Если обязательные критерии провалены и `attempts < VERIFY_MAX_ATTEMPTS` — переход
   `verifying → running`, повторный запуск с обратной связью: в промпт добавляются провалы
   и требование исправить; сессия сохраняется. Бюджет шагов/токенов/времени общий, проверка
   не отменяет лимитов.
4. Финальное состояние: `done` при `passed`/`not_required`; `partial` при `partial`/
   `unavailable`/`failed` после исчерпания попыток; `failed`, если исполнитель упал и
   результата нет. `partial` — не успех: отчёт прямо об этом говорит.
5. Результат проверки сохраняется в задаче и передаётся в `delivery`.
- Если проверка недоступна целиком (нет LibreOffice, нет команд) — задача может быть
  завершена как `partial` с пометкой «не проверено», но не как полностью проверенная.

### Отчёт
`delivery/composeReportText` получает `verification` и добавляет блок:
- «Проверка: …» — по типам; «не проверено: …» — список причин;
- при `partial` заголовок не «✅ выполнена», а «⚠️ выполнена частично: не пройдены проверки»;
- в подписи остаются время, шаги, токены, стоимость.

### Конфиг
`VERIFY` (true) — включить проверку; `VERIFY_MAX_ATTEMPTS` (1) — сколько раз пробовать
исправить; `VERIFY_TIMEOUT_MS` (300 000) — предел одной проверки; `VERIFY_RENDER` (true) —
рендер документов при требованиях к оформлению; `VERIFY_MODEL_MAX_CHARS` (12 000) — предел
текста для модельных проверок. Все ключи — в `config`, `.env.example`, README.

### Миграция и откат
- Записи без `criteria`/`verification` считаются задачами до проверки; новые поля
  появляются при следующей записи.
- Новые состояния `verifying`, `partial` читаются старым кодом как неизвестные подписи, но
  не ломают загрузку (журнал v2 из PLA-13); при откате задачи в этих состояниях считаются
  незавершёнными.
- Откат: симлинк на предыдущий релиз; `VERIFY=false` отключает проверку без откатa кода,
  возвращая прежнее поведение.

## Влияние
- Новый домен `src/verification/`; изменения в `src/core/bot.mjs`, `src/execution/`
  (критерии в промпте, порт проверок), `src/tools/` (инспекция документов/таблиц, рендер),
  `src/delivery/report.mjs`, `src/storage/tasks.mjs`, `src/config/`, тесты, README.
- Дороже: проверки добавляют время и, для исследования/оформления, токены. Бюджеты
  ограничены настройками; `VERIFY=false` — аварийный выключатель.
- Риск: ложный провал проверки из-за окружения — снижается статусом `unavailable` и
  явным «не проверено» вместо «ошибка результата».
- Риск: критерии расширяют задачу — закрывается тестом «критерии только из запроса и
  минимальной таблицы».

## Альтернативы
- Проверять всё моделью — дорого и ненадёжно; локальные проверки точнее и дешевле,
  модель — только для исследования/оформления.
- Встроить проверки в `execution` — смешивает исполнение и контроль, нарушает границы
  доменов; отвергнуто.
- Оставить проверку на усмотрение модели в промпте — не даёт доказуемого результата;
  отвергнуто.
- Новый внешний сервис — противоречит «ноль зависимостей»; отвергнуто.
