# Техническое решение

## Как устроено сейчас
Один процесс: `src/index.mjs` собирает зависимости и стартует `bot.mjs`. Внутри `bot.mjs`
— Telegram-поллинг, доступ владельца, маршрутизация команд, очередь задач, режим плана,
диалог, отчёты, голос, Диск, учёт расхода. Рядом 30 файлов-помощников: одни про
внешние API (`telegram.mjs`, `yandex-disk.mjs`), другие про исполнение (`dsh-task.mjs`,
`cgroup.mjs`, `prompt.mjs`), третьи про автономию (`observe.mjs`, `alerts.mjs`). Общих
правил импорта нет: `bot.mjs` тянет всё, помощники тянут друг друга.

## Предлагаемое решение

### Целевая схема

```
                        ┌──────────────┐
        Telegram ──────▶│ core         │  приём, доступ, маршрутизация, очередь, команды
                        └──────┬───────┘
                               │ порты
              ┌────────────────┼─────────────────┐
              ▼                ▼                 ▼
      ┌─────────────┐  ┌─────────────┐   ┌──────────────┐
      │ execution   │  │ delivery    │   │ autonomy     │
      │ DSH, cgroup │  │ текст,файлы │   │ наблюдатель, │
      │ промпт, reply│ │ голос, Диск │   │ триггеры     │
      └──────┬──────┘  └──────┬──────┘   └──────┬───────┘
             ▼                ▼                 ▼
      ┌─────────────┐  ┌───────────────────────────────┐
      │ tools       │  │ storage                       │
      │ вложения,   │  │ журналы, память, учёт, наблюд.│
      │ OCR, голос  │  └───────────────────────────────┘
      └──────┬──────┘
             ▼
      ┌──────────────────────────────────────────┐
      │ integrations  Telegram·Диск·модель·STT   │
      │ bot-link      протокол бот↔агент, сторож │
      └──────────────────────────────────────────┘
             ▲
      ┌──────┴──────┐
      │ config      │  настройки и политика (все домены читают только отсюда)
      └─────────────┘
```

### Правила
1. `core` не содержит правил: только маршрутизация и ответ.
2. Сеть — только в `integrations` и только за портом.
3. `storage` — единственный писатель состояния (атомарно, с версией схемы).
4. `delivery` — единственное место, которое решает, как выглядит ответ.
5. `config` читается один раз и валидируется при старте.
6. Домен тестируется без сети: порты подменяются в тестах.

### Карта файлов
Полная таблица «домен → ответственность → файлы» — в `specs/architecture/spec.md`.

### Очередь изменений
Каждый пункт — отдельная папка change, поведение не меняется, после каждого — тесты и
деплой. Зависимости указаны явно.

| № | Изменение | Содержание | Зависит от |
|---|---|---|---|
| 1 | `extract-config` | `config.mjs` → домен настроек, политика и лимиты; чтение env только там | — |
| 2 | `extract-storage` | `state/memory/tasks/usage/pricing` → домен хранения, атомарная запись, версия схемы | 1 |
| 3 | `extract-integrations` | Telegram, Диск, модель, SpeechKit, HTTP-приём — за порты | 1 |
| 4 | `extract-execution` | DSH, cgroup, промпт, reply-протокол, быстрый слой, рабочая папка | 1, 3 |
| 5 | `extract-tools` | вложения, vision/OCR, извлечение, офисные документы, голос | 3 |
| 6 | `extract-delivery` | ответ, файлы, голос, архив, подписи и стоимость | 2, 3 |
| 7 | `extract-bot-link` | протокол бот↔агент, notify/outbox, сторож, туннели | 3, 6 |
| 8 | `extract-autonomy` | наблюдатель и алерты за портами, CLI таймеров | 2, 3 |
| 9 | `slim-core` | `bot.mjs` — только оркестрация и команды | 4–8 |
| 10 | `openspec-tooling` | `tools/spec-check`, `_template`, `AGENTS.md` в корне репо | — |

## Влияние
- Поведение не меняется по требованию: каждый шаг — перенос кода и тестов, а не переписывание.
- Риск: на шаге 9 (`slim-core`) можно потерять неочевидную проводку — поэтому он последний
  и делается с живой проверкой всех команд.
- Откат: переключение симлинка `/opt/agent` на предыдущий релиз (`deploy/install-remote.sh`
  ставит новый релиз отдельной папкой).
- Деплой: не нужен для этого изменения (только документы и структура).

## Альтернативы
- **Оставить как есть** — дешевле сейчас, но `bot.mjs` растёт и каждый новый инструмент
  увеличивает связность; тесты продолжают проверять платформу, а не правила.
- **Переписать на TypeScript с DI-контейнером** — даст строгие границы, но тянет
  зависимости и ломает «ноль npm в рантайме»; для домашнего проекта это лишнее.
- **Микросервисы** — усложнят деплой и состояние; домены как папки + порты дают те же
  границы без сетевой цены.
