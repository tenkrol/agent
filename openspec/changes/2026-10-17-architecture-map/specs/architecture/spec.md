# Дельта для домена architecture

Границы доменов агента, направление зависимостей и правила, которые нельзя нарушать.
Это карта, по которой раскладывается существующий код (`src/*`, `deploy/*`), а не новый
слой: поведение агента от этого не меняется.

## Домены

| Домен | Ответственность | Куда migrates из |
|---|---|---|
| `core` | приём сообщений, доступ владельца, маршрутизация, очередь задач, команды, сессии диалога | `src/bot.mjs` |
| `execution` | исполнение задачи: запуск DSH, cgroup, сборка промпта, разбор ответа, быстрый слой, рабочая папка задачи | `src/dsh-task.mjs`, `src/cgroup.mjs`, `src/prompt.mjs`, `src/reply-protocol.mjs`, `src/quick.mjs`, `src/workspace.mjs` |
| `tools` | инструменты агента: вложения, распознавание (vision, OCR), извлечение данных, офисные документы, голос | `src/inbox.mjs`, `src/vision.mjs`, `src/ocr.mjs`, `src/extract.mjs`, `src/stt.mjs`, `src/tts.mjs` |
| `integrations` | внешние подключения: Telegram, Яндекс.Диск, модель, SpeechKit, HTTP-приём моста, туннели | `src/telegram.mjs`, `src/platform.mjs`, `src/yandex-disk.mjs`, `deploy/setup-bridge-tunnel.sh`, `deploy/setup-outbox.sh` |
| `config` | настройки и политика: чтение и валидация окружения, лимиты, таймауты, режимы | `src/config.mjs` |
| `bot-link` | правила обмена с чат-ботом: формат задачи и отчёта, авторизация, сторож завершённых задач, обратная связь | `src/bridge-http.mjs`, `src/notify.mjs`, `deploy/agent-notify`, `deploy/agent-run-watch` |
| `storage` | состояние и учёт: журналы задач и расхода, память, наблюдения, состояние алертов, атомарная запись | `src/state.mjs`, `src/memory.mjs`, `src/tasks.mjs`, `src/usage.mjs`, `src/pricing.mjs` |
| `delivery` | доставка результата: текст ответа, файлы, голос, архив, подписи и стоимость | части `src/bot.mjs`, `src/format.mjs` |
| `autonomy` | наблюдатель и алерты: сбор метрик, базовая линия, триггеры, дедуп, тихие часы, сводка | `src/observe.mjs`, `src/alerts.mjs`, `src/alerts-cli.mjs`, `deploy/metrics-collect.sh` |
| `ops` | эксплуатация: деплой, бэкап, секреты, логирование, сборка зависимостей | `deploy/*`, `src/logger.mjs`, `src/index.mjs` |
| `workflow` | сам процесс разработки по OpenSpec | `openspec/` |

## ADDED Requirements

### Requirement: Ядро — только оркестрация
`core` ДОЛЖЕН принимать сообщение, определять сценарий, звать нужный домен и отправлять
ответ. Бизнес-правила (когда срабатывает напоминание, как считается стоимость, что
считать аномалией) в `core` находиться НЕ ДОЛЖНЫ.

#### Scenario: Новая команда
- GIVEN владелец просит добавить команду
- WHEN определяется место для правила
- THEN правило живёт в своём домене, а в `core` добавляется только маршрутизация и ответ

#### Scenario: Размер ядра
- GIVEN в `core` появляется функция, которая форматирует документы или ходит в сеть
- WHEN это замечается на ревью спеки
- THEN функция переносится в `tools` или `integrations`

### Requirement: Внешний мир — только через integrations
Сетевые вызовы ДОЛЖНЫ жить в `integrations` и быть скрыты за портом (интерфейсом).
Остальные домены получают порт и не знают имени и формата внешнего API.

#### Scenario: Смена провайдера
- GIVEN нужно заменить провайдера распознавания речи
- WHEN правка внесена в `integrations`
- THEN домены `tools` и `execution` не меняются
- AND тесты доменов проходят без сети

### Requirement: Направление зависимостей
Разрешено: `core → execution → tools → integrations`, `delivery → integrations`,
`autonomy → storage`, `bot-link → integrations`, все домены → `config`. Обратные
зависимости (например, `integrations → core`) запрещены; циклические — запрещены.

#### Scenario: Импорт «назад»
- GIVEN агент хочет из `integrations` импортировать функцию из `core`
- WHEN это происходит
- THEN правило нарушено: нужная функция переносится в общий домен (`tools`, `storage`)
  или в порт

### Requirement: Настройки читаются один раз
`config` ДОЛЖЕН один раз прочитать окружение, провалидировать значения и отдать
остальным доменам готовый объект. Чтение `process.env` вне `config` (кроме тестов) НЕ
ДОПУСКАЕТСЯ.

#### Scenario: Новая переменная
- GIVEN нужна новая настройка
- WHEN она добавляется
- THEN она описана в `config`, в `.env.example` и в README, с значением по умолчанию
- AND неверное значение даёт понятную ошибку при старте

### Requirement: Состояние — только через storage
Запись журналов и состояния ДОЛЖНА идти через `storage` (атомарная запись, версия схемы,
защита битых файлов). Прямая запись в `state/*.jsonl` из других доменов ЗАПРЕЩЕНА.

#### Scenario: Новый журнал
- GIVEN нужен новый журнал
- WHEN он добавляется
- THEN писатель и читатель живут в `storage`
- AND формат описан в его спеке

### Requirement: Доставка результата — одно место
Каким будет ответ (одно сообщение или статусы, файлы, голос, архив) решает `delivery`.
Домены исполнения возвращают результат, а не шлют его в Telegram сами.

#### Scenario: Режим отчёта
- GIVEN включён режим «одно сообщение на задачу»
- WHEN задача завершилась
- THEN ровно одно сообщение формирует `delivery`
- AND исполнение не отправляет ничего напрямую

### Requirement: Домен тестируется без сети
Тесты домена ДОЛЖНЫ проходить без сети, без настоящего DSH и без фейковой платформы:
зависимости подменяются портами.

#### Scenario: Тест триггеров алертов
- GIVEN тест проверяет срабатывание триггера
- WHEN он запускается
- THEN используются синтетические замеры и порт уведомлений
- AND сеть и Telegram не задействованы
