# Техническое решение

## Как устроено сейчас
- Вход: `BotLinkServer` (`bridge-http.mjs`) принимает `POST /bridge` с `{task, source}`,
  проверяет bearer-токен и длину, зовёт `bot.submitBridgedTask`, отвечает `202 {taskId}`.
- Задача из моста выполняется как личная задача владельца: `chatId` = личный чат
  владельца, `variantsMode: 'never'`, `freshSession: true`. Вопрос задать нельзя, вариантов
  нет.
- Выход: `reportResult`/`parkForAnswer`/`parkForVariants` вызывают
  `mirrorResult` → `mirrorToAssistant` → `postOutbox` (`integrations/outbox.mjs`): один
  `POST /outbox` с `{text, title}`, текст обрезается до 3500 символов, ответ ассистента не
  анализируется (`ok`/`status`), повторов нет.
- Маршрут исходного разговора нигде не хранится: `chatId` задачи — это личный чат агента,
  а не разговор ассистента. Идентификатора события нет.
- Состояние задачи и факт доставки смешаны: `done` ставится до отправки, ошибка доставки
  только логируется, повторить отправку без повторного выполнения нельзя.
- Входные и выходные файлы через контракт не передаются; ревизий нет.

## Предлагаемое решение

### Модули
```
src/bot-link/
  protocol.mjs     разбор и валидация запросов /v1 (tasks, reply, cancel, files)
  files.mjs        приём и выдача файлов: multipart, лимиты, fileId
  bridge-http.mjs  маршруты /v1/* и прежний /bridge (совместимость)
  route.mjs        маршрут ответа: проверка и хранение
  events.mjs       сборка событий: пользовательские result/question, служебное memory_proposal
  deliver.mjs      воркер доставки: ассистент и личный чат, повторы, ack, восстановление
  mirror.mjs       прежнее зеркалирование (совместимость, тонкая обёртка)
src/storage/
  deliveries.mjs   журнал доставок: канал, состояние, попытки, восстановление sending
  requests.mjs     ключи идемпотентности с областью submit|reply|cancel
  files.mjs        реестр файлов контракта: fileId, метаданные, срок хранения
  tasks.mjs        поля route, version, rootTaskId, revisionOf, resultSummary
src/integrations/
  outbox.mjs       postAgentEvent (контракт v2) + postOutbox (прежний)
```

### Входящие маршруты
- `GET /v1/health`, `GET /v1/capabilities` — без токена только health, как сейчас.
- `POST /v1/files` — `multipart/form-data`, поле `file`, лимит `FILES_MAX_BYTES`;
  сохраняется в каталог входных файлов состояния, в реестр пишется `fileId`; ответ `201`.
- `GET /v1/files/:id` — с токеном отдаёт файл из реестра; `404` для неизвестного, `410` для
  истёкшего срока.
- `POST /v1/tasks` — валидация `contract: 2`, `requestId`, `task`, `route`, `attachments[].fileId`,
  `context.facts` (массив объектов `{ text, subject?, validUntil? }`, как в PLA-17);
  создание задачи через `accept()` из PLA-13; ответ `202` после сохранения.
- `GET /v1/tasks/:id` — состояние из журнала: `execution`, `delivery`, `question`,
  `result`, `version`, `rootTaskId`, `revisionOf`.
- `POST /v1/tasks/:id/reply` — ответ на вопрос: продолжение той же задачи с сохранённой
  сессией (как `continueTask`), `202`; `requestId` обязателен.
- `POST /v1/tasks/:id/cancel` — остановка выполнения/ожидания, `200`; `requestId`
  обязателен, повтор идемпотентен, отдельного пользовательского события нет.
- `POST /bridge` — прежний запрос; маппится во внутреннюю задачу без `route` с
  `source: legacy`; `requestId` необязателен, ответ прежний.

Авторизация: тот же bearer-токен, `timingSafeEqual`; лимиты тела, длины и файла — из
конфига. `route` проверяется по настройке ассистента (`BRIDGE_ROUTE_BOT_ID`,
`BRIDGE_ROUTE_CHAT_ID`); чужой маршрут — `400`.

### Ключи идемпотентности
- Ключ `submit` продолжает храниться в записи задачи (`requestKey` из PLA-13) и остаётся
  источником для повтора постановки; второго хранилища для него не заводится.
- Для `reply` и `cancel` добавляется журнал `storage/requests.mjs` (`requests.jsonl`),
  реестр ключей `requestKeys`: `{ scope, key, taskId, response, at }`, где `scope` —
  `reply` или `cancel`. Ключ в одной области уникален.
- Запись ключа идёт до ответа клиенту: сначала долговечно сохраняется результат, потом
  ответ.
- Повтор с тем же ключом возвращает сохранённый ответ (`submit` — `taskId` и
  `duplicate: true`; `reply`/`cancel` — прежний статус), второго выполнения нет.
- Тот же ключ с другим телом — `409`; тело сверяется по хэшу запроса.
- Ключ `submit` для прежнего `/bridge` необязателен; без него дедупликации нет (как в
  PLA-13), это логируется.
- При загрузке ключи `reply`/`cancel` читаются из `requests.jsonl`, ключи `submit` — из
  записей задач (PLA-13); записи без ключей не мешают.

### Файлы
- Загрузка: `POST /v1/files`, поле `file`, имя и MIME из multipart, ограничение
  `FILES_MAX_BYTES`; файл кладётся в `state/files/input/<fileId>` (права 600), в реестр —
  `fileId`, имя, MIME, размер, направление, `expiresAt`.
- Задача получает вложения по `fileId`: ядро копирует файл в `inbox/` рабочей папки задачи
  (как обычное вложение) и передаёт путь инструментам. Произвольные пути и URL
  отклоняются.
- Результат: файлы, собранные `collectOutputs`, регистрируются в `state/files/result/` и
  получают `fileId`; событие `result` содержит `fileId`, имя, размер, MIME, подпись.
  Скачивание — `GET /v1/files/:id` с токеном, срок — `OUTPUT_RETENTION_DAYS`.
- Уборка: реестр и файлы чистятся по сроку; запись помечается истёкшей, `GET` даёт `410`.
- Лимит диска: перед сохранением проверяется свободное место; ошибка — `503` для загрузки,
  а не падение сервиса.

### Маршрут и диалог
- Запись задачи получает `route` (платформа, бот, чат, тред, сообщение) и
  `source: assistant`. Вопрос, варианты и результат уходят по этому маршруту; личный чат
  агента остаётся для личных задач.
- Для задачи с маршрутом `variantsMode` больше не форсируется в `never`: уточняющий вопрос
  и варианты разрешены, сессия сохраняется для продолжения. План на утверждение по-прежнему
  не показывается (утверждать некому).
- Вопрос доставляется событием `question`; ответ приходит `POST /v1/tasks/:id/reply` и
  будит ту же задачу (тот же `id`, тот же `sessionId`), а не создаёт новую.
- Отмена — только состояние, читаемое через `GET /v1/tasks/:id`; пользовательского события
  отмены нет.
- Если `route` нет (личная задача), поведение прежнее: вопрос в чате агента, ответ
  сообщением.

### События
- Пользовательские события — только `result` и `question`; они создают сообщение в исходном
  разговоре. Текст результата обрезается до `DELIVERY_TEXT_CHARS` (3500) и отправляется с
  заголовком «Ответ агента» — прежнее поведение сохраняется.
- `eventId` единый: `<taskId>:<type>:<version>`, без sequence; версия — версия результата
  задачи. Повтор всегда с тем же идентификатором.
- Служебное событие `memory_proposal` (для PLA-17): `proposal {text, subject?, kind, scope}`,
  без `text`/`title` пользовательского сообщения. Отправляется только если ассистент
  объявил `capabilities.serviceEvents`; иначе не отправляется и не считается ошибкой.
- Ответ ассистента `{ok, eventId, processed, duplicate}`; `processed: true` — `ack`, после
  него повторов нет. Ошибка `4xx` — терминальная (`failed`), `5xx`/сеть — повтор по
  `DELIVERY_RETRY_MS` до `DELIVERY_MAX_ATTEMPTS`.
- Старый приёмник без `ack`: получает `200`, агент фиксирует `sent` без подтверждения;
  служебные события ему не отправляются.

### Доставка как отдельное состояние
- `src/storage/deliveries.mjs` — append-only `deliveries.jsonl`:
  `{ version, eventId, taskId, type, channel: 'assistant'|'personal', route, payload, state,
  attempts, nextAttemptAt, createdAt, sentAt, ackedAt, outcome, lastError }`. Последняя
  строка для `eventId` побеждает.
- Состояния: `pending → sending → sent → acked | failed`. `sent` — передано, ack нет;
  `outcome: 'unknown'` — подтверждение не сохранилось.
- Воркер `deliver.mjs` (тик `DELIVERY_TICK_MS`): выбирает `pending` с
  `nextAttemptAt <= now`, отправляет через `postAgentEvent` (ассистент) или
  `platform.sendText`/`sendDocument` (личный чат), обновляет запись. Расписание повторов
  `DELIVERY_RETRY_MS`, не больше `DELIVERY_MAX_ATTEMPTS`. Ошибка `4xx` ассистента —
  терминальная.
- После рестарта запись `sending` не остаётся в этом состоянии: исход считается неизвестным
  (`sent` + `outcome: 'unknown'`), задача не блокируется, повтор идёт по правилам.
- Перед отправкой пишется действие в журнал PLA-13 (`started`), после ответа —
  `confirmed`; так повтор после сбоя не теряет факт отправки.
- Выполнение и доставка независимы: смена `delivery.state` никогда не меняет `execution`;
  повтор доставки не запускает исполнителя. При старте воркер подхватывает незавершённые
  доставки.
- Личная доставка в Telegram учитывается тем же журналом (канал `personal`) и имеет
  ограниченный повтор; абсолютной гарантии отсутствия дублей нет — если процесс упал между
  `sendMessage` и подтверждением, повтор может создать второе сообщение. Ограничение
  фиксируется в отчёте и документации.
- Если доставка ассистенту окончательно не удалась, владелец получает уведомление в личный
  чат агента (канал `personal`, отдельная запись) с идентификатором задачи и причиной.
- Ручной повтор: `/deliver <taskId>` — поставить события задачи в очередь повторно.

### Политика операций
Задача от ассистента не отличается по правам от личной: тот же `cwd`, та же рабочая папка,
тот же запрет сети/секретов/серверов, те же лимиты. Контракт лишь добавляет маршрут и
файлы; он не даёт новых инструментов и не расширяет песочницу. Это проверяется тестом
границ (попытка сети/секрета/пути вне рабочей папки).

### Ревизии результата
- `POST /v1/tasks` с `revisionOf` и обязательным `requestId`:
  - проверяется, что прошлая задача существует и её результат доступен;
  - создаётся задача с `rootTaskId` (корень), `revisionOf`, `version = прошлая + 1`;
  - в промпт добавляется прошлый результат (текст, список файлов, `fileId`) и просьба
    изменить только запрошенное;
  - файлы прошлой версии берутся из реестра/рабочей папки; если их уже нет по сроку
    хранения — задача всё равно создаётся, а в отчёте явно сказано, что прошлый файл
    недоступен.
- `GET /v1/tasks/:id` показывает версию и связь; прежняя версия и её файлы остаются
  доступны согласно `OUTPUT_RETENTION_DAYS`.

### Совместимость и порядок выката
1. Чат-бот первым получает приём событий v2 с дедупликацией и `ack`, загрузку/скачивание
   файлов и служебные события (своё изменение в `tenkrol/assistant`); старый `/outbox` он
   тоже принимает.
2. Агент выкатывается с `CONTRACT_V2=true`: `/v1/*`, файлы и события работают, `/bridge` и
   `/outbox`-текст сохраняются.
3. Старый ассистент: задача через `/bridge` без `route`, результат текстом через
   `/outbox`; событие содержит поле `text`, поэтому доставка не ломается; файлы и служебные
   события ему не отправляются.
4. Откат агента — симлинк на предыдущий релиз; контракт v1 остаётся в коде до отдельного
   решения об удалении.

### Конфиг
`CONTRACT_V2` (true), `BRIDGE_ROUTE_BOT_ID`, `BRIDGE_ROUTE_CHAT_ID`,
`DELIVERY_TICK_MS` (30 000), `DELIVERY_RETRY_MS` (список), `DELIVERY_MAX_ATTEMPTS` (8),
`DELIVERY_TEXT_CHARS` (3500), `FILES_MAX_BYTES` (20 МиБ). Все ключи — в `config`,
`.env.example`, README; дельта домена `config` — `specs/config/spec.md`.

### Миграция и откат
- Старые записи журнала не имеют `route` — считаются личными задачами; `version` = 1,
  `rootTaskId` = `id`.
- `deliveries.jsonl`, `requests.jsonl`, реестр файлов создаются пустыми; доставки и ключи,
  начатые старым кодом, неизвестны — при первом запуске новых незавершённых нет.
- Файлы нового контракта хранятся в `state/files/`; старые вложения остаются в рабочей
  папке и не мигрируются.
- Откат: предыдущий релиз агента; события, отправленные v2-агентом, старый ассистент
  получит как обычный текст (поле `text` есть). Задачи, созданные через `/v1/*`, старому
  коду видны как обычные записи журнала; файлы и ключи остаются на диске до уборки.

## Влияние
- Меняются `src/bot-link/*`, `src/integrations/outbox.mjs`, `src/storage/` (журнал доставок,
  ключи запросов, реестр файлов, поля задачи), `src/core/bot.mjs` (воркер, маршрут,
  ревизии, вопросы из моста, аварийные уведомления), `src/config/`, тесты, README и
  `.env.example`.
- Ассистент обязан обновиться, чтобы получить адресность, вопросы, файлы, дедупликацию и
  `ack`; без его обновления работает прежний сценарий (личный чат + текст), это проверяется
  тестом совместимости.
- Риск: ошибка маршрута отправит результат не в тот чат — закрывается проверкой `route` по
  настройке и тестами на чужой/пустой маршрут.
- Риск: файлы занимают диск — закрывается лимитом `FILES_MAX_BYTES`, сроком хранения,
  проверкой свободного места и уборкой.
- Риск: повтор события после `ack` без дедупликации у ассистента — закрывается постоянным
  `eventId` и требованием к ассистенту.
- Риск: задача от ассистента пытается выйти за политику — закрывается общим тестом границ.

## Альтернативы
- Оставить один `POST /bridge` и добавить поля — не даёт версионирования и состояния;
  отвергнуто.
- Передавать файлы base64 внутри JSON — раздувает тело, ломает лимит 64 КиБ и память;
  отвергнуто в пользу `/v1/files`.
- Считать служебные события обычными сообщениями — старый приёмник показал бы их
  пользователю; отвергнуто: служебные события без `text` и по отдельной возможности.
- Хранить ключи идемпотентности только в памяти — после рестарта повтор создал бы дубль;
  отвергнуто в пользу постоянного журнала.
- Отдельная очередь сообщений (Redis/брокер) — ноль зависимостей в рантайме и лишняя
  инфраструктура; отвергнуто в пользу журнала на диске.
- Доставлять результат только через личный чат агента и не возвращать в разговор —
  противоречит требованию «возврат в исходный разговор»; отвергнуто.
- Опрашивать ассистента (`GET /outbox`) — на его стороне нет очереди, лишний цикл;
  отвергнуто в пользу push с `ack`.
