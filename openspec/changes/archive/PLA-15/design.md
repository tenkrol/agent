# Техническое решение

## Как устроено сейчас
- `executeTask` (`src/core/bot.mjs`) после `runner.run` считает успех по `result.ok` и
  `exitCode`: разбирает ответ (`parseReply`), собирает файлы (`collectOutputs`), ставит
  `done`, отправляет текст и файлы. Ни одна проверка содержимого не выполняется.
- `delivery/report.mjs` собирает заголовок, тело, диагностику и подпись; поля «проверено»
  нет.
- `execution/dsh-task.mjs` — запуск DSH в cgroup с таймаутом; `execution/quick.mjs` — быстрый
  слой; `tools/` умеет извлекать текст из DOCX/XLSX/PDF и распознавать изображения, но не
  проверять результат.
- LibreOffice и venv (python-docx, openpyxl, python-pptx) на сервере есть; офисные проверки
  можно выполнять локально.

## Предлагаемое решение

### Новый домен verification
```
src/verification/
  criteria.mjs    вывод проверяемых критериев из запроса и типа результата
  index.mjs       оркестрация проверки: verify({ criteria, files, ports }) → результат
  document.mjs    проверка документа
  spreadsheet.mjs проверка таблицы
  code.mjs        проверка изменения кода
  research.mjs    проверка исследования
```
Домен не импортирует другие домены: ядро передаёт ему критерии, файлы и порты. Порты
объявляются как интерфейсы и реализуются в своих доменах; каждый файловый порт получает
корень задачи (`root` — рабочая папка задачи) и сам проверяет путь:
- `ports.inspectDocument({ root, path })` → `{ opens, text, sections, pages }`
  (реализация — `tools`);
- `ports.renderDocument({ root, path, to })` → путь к PDF/PNG (реализация — `tools`);
- `ports.inspectSpreadsheet({ root, path })` → `{ opens, sheets, values, formulas, errors }`
  и `ports.recalcSpreadsheet({ root, path })` (реализация — `tools`);
- `ports.runCodeChecks({ root, cwd, commands, timeoutMs })` → `{ checks: [{ command,
  exitCode, stdout, stderr }] }` (реализация — `execution`, процессы в cgroup);
- `ports.askModel(prompt)` → текст (реализация — `integrations`, для критериев и
  исследования);
- `ports.now()`.
Изоляция путей: порт обязан разрешить `path`/`to` относительно `root`, отклонить выход за
его пределы (включая `..` и символические ссылки наружу) и вернуть ошибку «вне рабочей
папки». `runCodeChecks` получает тот же `root` и не запускается с `cwd` вне него.
Направление зависимостей не нарушается: `core` вызывает `verification` и передаёт порты,
реализованные в `tools`/`execution`/`integrations` на сборке.

### Критерии результата
`criteria.mjs` получает формулировку владельца, тип результата и (если есть) план; выводит
`[{ id, text, kind, required, source }]`:
- `kind`: `format`, `sections`, `sources`, `data`, `computation`, `checks`, `other`;
- `required`: обязательные (по умолчанию) и дополнительные;
- `source` — фраза владельца, из которой критерий выведен, либо «минимальная проверка типа».
Минимальные проверки типов — из таблицы требований (документ открывается и содержит
требуемые разделы; таблица открывается, данные на месте, формулы пересчитаны; код —
подходящие проверки выполнены; исследование — выводы связаны с источниками, предположения
отделены).
Критерии не расширяют объём: `criteria.mjs` не добавляет требования, которых нет в
запросе или в минимальной таблице. Существенная неоднозначность (неясно, какой формат,
какие разделы, обязателен ли файл) — один вопрос владельцу через существующий протокол
`ВОПРОС:`; задача паркуется, выполнение не начинается.
Критерии сохраняются в записи задачи (`criteria`), попадают в промпт исполнителя
(`execution/prompt.mjs`) и в результат проверки.

### Проверка по типам
- **Документ**: открывается (ZIP/XML для DOCX, LibreOffice для ODT/PDF); требуемые разделы
  находятся в тексте; при значимых требованиях к оформлению — рендер в PDF/PNG и проверка
  отображения (порт `renderDocument` + vision через `askModel`; если vision недоступен —
  `unavailable`).
- **Таблица**: открывается; листы/данные на месте; формулы пересчитаны LibreOffice
  (`recalcSpreadsheet()`), значения сравнены с ожидаемыми; ошибки `#REF!`, `#VALUE!`,
  `#DIV/0!` — провал; при требованиях к формату проверяется отображение.
- **Код**: критерии `checks` превращаются в команды из allowlist (тесты, линтер, сборка) и
  запускаются портом `execution` в cgroup с таймаутом; фиксируются команды, коды возврата,
  хвосты вывода; проверки, которые нельзя выполнить, — `unavailable`, а не «успех».
- **Исследование**: в ответе есть раздел источников; выводы связаны с источниками
  (модель-проверяющий с портом `askModel` и списком источников); предположения отделены от
  подтверждённых сведений; отсутствие источников — провал, если они требовались.

### Allowlist команд проверок
Команды проверок кода НЕ ДОЛЖНЫ подбираться произвольно моделью или из текста задачи.
Разрешённый набор задаётся конфигом `VERIFY_CHECK_ALLOWLIST` (значение по умолчанию —
типовые проверки известных типов проектов: `node --test`, `npm test`, `npm run lint`,
`npm run build`, `pytest`, `go test`, `cargo test`, `make test`), команда сравнивается по
нормализованной строке/argv без оболочки:
- команда из allowlist запускается в cgroup с таймаутом `VERIFY_TIMEOUT_MS`;
- команда вне allowlist НЕ запускается, критерий получает статус `unavailable` с причиной
  «команда не разрешена», а не «пройдено»;
- произвольные shell-строки, подстановки и составные команды запрещены: порт принимает
  argv-массив и не использует shell;
- если allowlist пуст, проверки кода недоступны (статус `unavailable`), а не «разрешено
  всё».
Список по умолчанию покрывает типовые проекты; расширение — только явной настройкой
владельца.

Результат проверки:
```json
{
  "status": "passed | failed | partial | unavailable | not_required | disabled",
  "criteria": [{ "id": "c1", "status": "passed|failed|unavailable|skipped", "evidence": "...",
                 "notes": "..." }],
  "attempts": 1,
  "checkedAt": 1760000000000,
  "limitations": ["что именно не удалось проверить"]
}
```
`status` вычисляется по обязательным критериям: все прошли — `passed`; часть не прошла или
недоступна — `partial`; ни один обязательный не проверен — `unavailable`; проверки не
требуются — `not_required`; проверка выключена настройкой — `disabled` с причиной
`VERIFY=false`.

### Когда проверка обязательна
Применимость проверки определяется до запуска и не зависит от желания модели «что-то
проверить»:
- **Тип результата** — по созданным файлам и расширениям, затем по формулировке:
  `docx`, `odt`, `pdf` → документ; `xlsx`, `ods`, `csv` → таблица; файлы кода
  (`.mjs`, `.js`, `.py`, `.go`, `.rs` и т. п.) или запрос «правка кода / тесты / сборка» →
  код; нет файлов-артефактов, но запрос просит анализ, сравнение или источники →
  исследование.
- **Сложное поручение** — когда есть критерии сверх минимальной проверки типа (разделы,
  формат, источники, формулы) ИЛИ результат-файл ИЛИ изменение кода ИЛИ исследование.
  Простой текстовый ответ без артефакта и без дополнительных критериев — `not_required`:
  проверка не выполняется, но это не «недоступная» проверка и не повод для `partial`.
- **Смешанный результат** — проверяются все применимые типы; неприменимые критерии не
  изобретаются.
- **`VERIFY=false`** — осознанный выключатель: задача завершается `done` без проверки, но
  отчёт (и событие ассистенту) ДОЛЖНЫ явно содержать «проверка отключена (VERIFY=false)».
  Тихий обход запрещён: `verification` сохраняется в задаче со статусом `disabled` и
  причиной, чтобы `/task <id>` и аудит видели, что проверки не было.

### Оркестрация в core
1. После подготовки задачи (до запуска) — критерии; при вопросе задача паркуется.
2. Применимость (см. выше): если `not_required` или `disabled` — ветка проверки
   закрывается, переход в `verifying` не выполняется.
3. После успешного `runner.run` — переход `running → verifying`, вызов
   `verification.verify`.
4. Если обязательные критерии провалены и `attempts < VERIFY_MAX_ATTEMPTS` — переход
   `verifying → running`, повторный запуск с обратной связью: в промпт добавляются провалы
   и требование исправить; сессия сохраняется. Бюджет шагов/токенов/времени общий, проверка
   не отменяет лимитов.
5. Финальное состояние: `done` при `passed`/`not_required`; `partial` при `partial`/
   `unavailable`/`failed` после исчерпания попыток; `failed`, если исполнитель упал и
   результата нет. `partial` — не успех: отчёт прямо об этом говорит. При `disabled`
   (`VERIFY=false`) — `done` без проверки.
6. Результат проверки сохраняется в задаче и передаётся в `delivery`.
- Если проверка недоступна целиком (нет LibreOffice, нет команд) — задача может быть
  завершена как `partial` с пометкой «не проверено», но не как полностью проверенная.

### Отчёт
`delivery/composeReportText` получает `verification` и добавляет блок:
- «Проверка: …» — по типам; «не проверено: …» — список причин;
- при `partial` заголовок не «✅ выполнена», а «⚠️ выполнена частично: не пройдены проверки»;
- при `disabled` (`VERIFY=false`) — строка «Проверка отключена (VERIFY=false)», чтобы
  владелец видел отсутствие проверки, а не считал результат проверенным;
- при `not_required` — «Проверка не требуется для этого результата» (не путать с
  «не проверено»);
- в подписи остаются время, шаги, токены, стоимость.

### Конфиг
- `VERIFY` (true) — включить проверку; при `false` задача завершается `done` без проверки,
  но отчёт явно помечает «проверка отключена».
- `VERIFY_MAX_ATTEMPTS` (1) — сколько раз пробовать исправить.
- `VERIFY_TIMEOUT_MS` (300 000) — предел одной проверки.
- `VERIFY_RENDER` (true) — рендер документов при требованиях к оформлению.
- `VERIFY_MODEL_MAX_CHARS` (12 000) — предел текста для модельных проверок.
- `VERIFY_CHECK_ALLOWLIST` — список разрешённых команд проверок кода: argv-команды,
  разделённые `;`, без оболочки; по умолчанию типовые проверки известных типов проектов;
  пустое значение = проверки кода недоступны.
Все ключи — в `config` (дельта `specs/config/spec.md`), `.env.example` и README; неверное
значение даёт ошибку при старте.

### Миграция и откат
- Записи без `criteria`/`verification` считаются задачами до проверки; новые поля
  появляются при следующей записи.
- Новые состояния `verifying`, `partial` читаются старым кодом как неизвестные подписи, но
  не ломают загрузку (журнал v2 из PLA-13); при откате задачи в этих состояниях считаются
  незавершёнными.
- Откат: симлинк на предыдущий релиз; `VERIFY=false` отключает проверку без откатa кода,
  возвращая прежнее поведение (с явной пометкой в отчёте).

## Влияние
- Новый домен `src/verification/`; изменения в `src/core/bot.mjs`, `src/execution/`
  (критерии в промпте, порт проверок с allowlist), `src/tools/` (инспекция документов и
  таблиц, рендер с проверкой пути внутри `root`), `src/delivery/report.mjs`,
  `src/storage/tasks.mjs`, `src/config/`, тесты, README.
- Дороже: проверки добавляют время и, для исследования/оформления, токены. Бюджеты
  ограничены настройками; `VERIFY=false` — аварийный выключатель, а не тихий обход.
- Риск: ложный провал проверки из-за окружения — снижается статусом `unavailable` и
  явным «не проверено» вместо «ошибка результата».
- Риск: критерии расширяют задачу — закрывается тестом «критерии только из запроса и
  минимальной таблицы».

## Альтернативы
- Проверять всё моделью — дорого и ненадёжно; локальные проверки точнее и дешевле,
  модель — только для исследования/оформления.
- Встроить проверки в `execution` — смешивает исполнение и контроль, нарушает границы
  доменов; отвергнуто.
- Оставить проверку на усмотрение модели в промпте — не даёт доказуемого результата;
  отвергнуто.
- Новый внешний сервис — противоречит «ноль зависимостей»; отвергнуто.
