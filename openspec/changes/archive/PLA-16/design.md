# Техническое решение

## Как устроено сейчас
- `ScheduleStore` (`src/core/schedule.mjs`) хранит `{id, cron, task, title, enabled,
  nextRunAt, runs, missed}`; тик `tickSchedules` создаёт задачу с `text: record.task`,
  `variantsMode: 'never'`, `freshSession: true`. Никаких параметров, формата результата и
  критериев у расписания нет.
- `/retry` создаёт новую задачу с `retryOf`; доработка результата в PLA-14 создаёт ревизию.
- Проверка результата (PLA-15) получает критерии из запроса владельца.

## Предлагаемое решение

### Новый домен procedures
```
src/procedures/
  index.mjs     сборка: validate, render, run
  validate.mjs  проверка полей, параметров и ограничений
  render.mjs    подстановка параметров в шаблон, сборка критериев
src/storage/
  procedures.mjs  атомарное хранение процедур и версий
```
Правила домена: `core → procedures`, `procedures → storage`, `procedures → config`.
Процедура не импортирует `execution`, `tools` и `integrations`; она только описывает
задание.

### Модель данных
`procedures.json` (`version: 1`, атомарная запись, битый файл — копия и пустой старт):
```json
{
  "version": 1,
  "nextId": 3,
  "procedures": {
    "p1": {
      "id": "p1",
      "name": "weekly-review",
      "activeVersion": 1,
      "versions": [
        {
          "version": 1,
          "status": "active",
          "purpose": "еженедельный обзор",
          "taskTemplate": "Собери обзор за {{period}} по разделам …",
          "params": [
            { "name": "period", "description": "период обзора", "required": true,
              "default": null },
            { "name": "sources", "description": "источники", "required": false,
              "default": "…" }
          ],
          "resultFormat": "DOCX: разделы «Итоги», «Риски», «План»; источники в конце",
          "criteria": [
            { "id": "c1", "text": "есть разделы «Итоги», «Риски», «План»",
              "kind": "sections", "required": true,
              "source": "владелец: разделы «Итоги», «Риски», «План»" }
          ],
          "limits": { "taskTokenBudget": 200000, "taskMaxSteps": 12 },
          "createdAt": 1760000000000,
          "createdBy": "owner",
          "sourceTaskId": "101034-1a"
        },
        {
          "version": 2,
          "status": "draft",
          "purpose": "еженедельный обзор",
          "taskTemplate": "Собери обзор за {{period}} по разделам …",
          "params": [],
          "resultFormat": "DOCX: разделы «Итоги», «Риски», «План»; источники в конце",
          "criteria": [],
          "limits": { "taskTokenBudget": 200000, "taskMaxSteps": 12 },
          "createdAt": 1760000000000,
          "createdBy": "owner",
          "sourceTaskId": "101034-1a"
        }
      ],
      "createdAt": 1760000000000,
      "updatedAt": 1760000000000
    }
  }
}
```
Обязательные поля версии: `purpose`, `taskTemplate`, `resultFormat`, `criteria`, `limits`.
- Версия создаётся активной, только если ВСЕ обязательные поля выведены из задачи; если
  хотя бы одно не выведено — версия создаётся `status: draft`, `activeVersion` на неё не
  указывает, `run` недоступен.
- `status` версии: `draft` (заполняется), `active` (действует), `archived` (заменена).
  Активная и архивная версии неизменяемы; черновик можно дополнять на месте, пока он не
  активирован. `/procedure set` по активной версии создаёт новую версию-черновик, а не
  правит действующую.
- `activeVersion` указывает только на `active`-версию; `run` работает только с ней.
- `limits` не могут превышать глобальные (`TASK_TOKEN_BUDGET`, `TASK_MAX_STEPS`,
  `TASK_TIMEOUT_MS`) и не дают новых прав; валидация отклоняет превышение.
- `criteria` — критерии PLA-15 в том же формате: `id`, `text`, `kind`, `required`, `source`
  (фраза владельца или «минимальная проверка типа»); при запуске объединяются с критериями
  из конкретной задачи (критерии процедуры обязательны).

### Явное сохранение и активация
Сохранение — только по явной команде владельца, из уже выполненной задачи:
- `/procedure save <name> <taskId>` — берёт формулировку задачи, её критерии, формат
  результата и ограничения, создаёт версию 1. Обязательные поля версии: `purpose`,
  `taskTemplate`, `resultFormat`, `criteria`, `limits`. Всё, что выводится из задачи,
  заполняется сразу; чего вывести нельзя, не придумывается.
- Если все обязательные поля выведены — версия создаётся `active` и `run` доступен.
- Если хотя бы одного поля нет — версия создаётся `draft`; `activeVersion` на неё не
  указывает, `run` и расписание для неё недоступны, `/procedure show` показывает, каких
  полей не хватает.
- `/procedure set <name> <поле> <значение>` — заполняет черновик (`purpose`,
  `taskTemplate`, `resultFormat`, `limits`, `criteria`, `params`). Когда все обязательные
  поля заполнены, владелец явно активирует версию (`/procedure activate <name>` или
  подтверждение в ответ на `/procedure set`); после активации версия неизменяема.
  `/procedure set` по активной версии создаёт новый черновик, а не правит действующую.
- `/procedure edit <name> <taskId>` — создаёт новый черновик версии из другой задачи
  (например, после ручной правки результата).
- `/procedure list`, `/procedure show <name> [версия]` — просмотр (включая черновики и
  недостающие поля); `/procedure remove <name>` — удаление (история версий сохраняется по
  сроку хранения `PROCEDURES_RETENTION_DAYS`).
Диалогов с моделью для «сохранения» нет: источник — задача или явная команда, поэтому
процедура воспроизводима.

### Запуск
- `/procedure run <name> [ключ=значение …]` — только для процедуры с активной версией и
  заполненными обязательными полями; иначе отказ с перечнем недостающих полей
  («процедура не активирована: задайте формат результата и критерии»).
- Проверка параметров, рендер текста, создание задачи с
  `procedure: { id, version: activeVersion, params }`, `criteria` из версии, `limits` из
  версии (в пределах глобальных). Результат — обычная задача с проверкой PLA-15.
- Расписание: `/schedule add "0 9 * * 1" procedure:weekly-review period=неделя`.
  `ScheduleStore` получает поля `procedureId`, `procedureVersion` (пусто — следовать
  активной версии), `params`. При срабатывании создаётся отдельная задача; фактическая
  версия фиксируется в записи задачи (`procedure.version`). Расписание на черновик
  невозможно: при создании оно проверяет наличие активной версии.
- Изменение процедуры не меняет уже созданные задачи и запланированные вхождения: каждое
  вхождение берёт активную версию на момент запуска; версия в задаче — источник истины.
- Если `procedureVersion` в расписании задан явно, вхождения используют именно его
  (закреплённая версия), пока расписание не изменят.

### Разовая корректировка ≠ изменение процедуры
- Доработка результата (PLA-14, `revisionOf`) создаёт ревизию задачи и НЕ трогает
  процедуру.
- Процедура меняется только явными `/procedure save|edit|set` и `/procedure activate`;
  разовая просьба не активирует и не меняет версию.
- В отчёте задачи видно имя и версию процедуры: `[процедура weekly-review, версия 2]`.

### Связь с PLA-15
- Критерии процедуры передаются в `verification` вместе с критериями задачи.
- Формат результата и ограничения попадают в промпт (`execution/prompt.mjs`) как часть
  текста задачи: «формат результата», «критерии проверки».
- Если версия процедуры удалена/устарела — задача всё равно содержит её снимок; повторный
  запуск по старому расписанию использует сохранённый снимок.

### Конфиг
- `PROCEDURES_MAX_VERSIONS` (20) — сколько версий одной процедуры хранится; старые
  `archived`-версии сверх предела удаляются, кроме версий, на которые ссылаются задачи.
- `PROCEDURES_RETENTION_DAYS` (365) — срок хранения удалённых процедур и архивных версий.
Оба ключа читаются в `config` (дельта `specs/config/spec.md`), описаны в `.env.example` и
README; неверное значение — ошибка при старте. Предел версий и срок применяются к
архивным/удалённым записям и не могут привести к удалению версии, на которую ссылается
задача; `PROCEDURES_RETENTION_DAYS` не может быть меньше срока хранения результатов.

### Миграция и откат
- `procedures.json` новый; старые расписания остаются без процедуры.
- Записи задач без `procedure` — обычные задачи.
- Откат: симлинк на предыдущий релиз; `procedures.json` не читается старым кодом, новые
  задачи с процедурой старый код выполнит как обычный текст (в записи есть `request`), это
  документируется.

## Влияние
- Новый домен `src/procedures/`, `src/storage/procedures.mjs`, изменения `src/core/bot.mjs`
  (команды, расписания), `src/core/schedule.mjs` (поля процедуры), `src/execution/prompt.mjs`
  (формат/критерии), `src/config/`, тесты, README.
- Риск: испорченная процедура повторяется по расписанию — закрывается версиями, явной
  правкой и тем, что процедура не меняется от разовой просьбы.
- Риск: процедура пытается поднять лимиты — валидация отклоняет.
- Риск: версия меняется между вхождениями — в задаче фиксируется фактическая версия,
  воспроизводимость сохраняется.

## Альтернативы
- Хранить процедуру как текст в расписании — нет параметров, критериев и версий; отвергнуто.
- Хранить процедуры в памяти или в файле расписаний — смешивает сущности и ломает
  версионирование; отвергнуто.
- Автосохранение процедуры из любого повторяющегося запроса — противоречит требованию
  «только по явному запросу»; отвергнуто.
- Делать версии изменяемыми — невозможно доказать, что именно выполнялось; отвергнуто.
