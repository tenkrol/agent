# Техническое решение

## Как устроено сейчас
- `AgentBot.queue` — массив в памяти процесса; `QUEUE_LIMIT = 3`; задачи выполняются
  строго по одной (`drain`).
- `TaskJournal` (`src/storage/tasks.mjs`) — append-only JSONL `tasks.jsonl`; последняя строка
  для `id` побеждает; запись только в конце выполнения (`open` вызывается в `executeTask`,
  затем `update`/`close`). Схема строки — `version: 1`, статусы `running`, `awaiting_reply`,
  `done`, `failed`, `cancelled`, `timeout`, `expired`.
- `submitBridgedTask` генерирует `id`, проверяет лимиты в `enqueueJob`, кладёт job в массив и
  сразу возвращает `taskId`; мост отвечает `202`.
- Незавершённое выполнение при старте не распознаётся: запись остаётся `running`.
- Вопрос к владельцу хранится и в журнале (`status: awaiting_reply`), и в `state.json`
  (`await:<chatId>`); второй источник — кэш для быстрого ответа.
- Внешние действия (отправка результата в точку приёма, файлы в Telegram) не фиксируются
  до выполнения, поэтому после сбоя нельзя отличить «отправлено» от «не отправлено».

## Предлагаемое решение

### Состояния и переходы
Новая схема журнала (`version: 2`) задаёт состояния из требований:

| Состояние | Значение |
|---|---|
| `queued` | принята и сохранена, ждёт исполнителя |
| `running` | выполняется |
| `awaiting_owner` | ждёт ответа или выбора владельца |
| `verifying` | резерв под PLA-15, до него не используется |
| `done` | завершена, результат получен |
| `partial` | завершена частично (для PLA-15; до него не выставляется) |
| `failed` | ошибка; уточнение причины — в `reason` (`timeout`, `budget`, `steps`, …) |
| `cancelled` | отменена владельцем или истекло ожидание (`reason: expired`) |
| `interrupted` | выполнение оборвано сбоем/перезапуском |

Старые статусы при загрузке переносятся: `awaiting_reply → awaiting_owner`,
`timeout → failed` + `reason: timeout`, `expired → cancelled` + `reason: expired`.
Отдельных статусов `timeout` и `expired` больше нет, но подписи сохраняются: функция
`statusLabel(record)` учитывает `reason` и возвращает прежние «⌛ по таймауту» и
«🕓 ответа не дождалась»; `describeTask` и `/tasks`, `/task`, `/retry` используют её.
Это закрывается тестом на записи со всеми прежними статусами.

Каждый переход — метод `journal.transition(id, to, { reason, actor, patch })`:
- проверяет переход по таблице допустимых (`queued → running|cancelled|interrupted`,
  `running → done|failed|cancelled|interrupted|awaiting_owner|verifying`,
  `awaiting_owner → queued|cancelled` (ответ владельца возвращает задачу в очередь; отмена),
  `verifying → done|partial|failed|cancelled|interrupted|running` (`running` — повтор на
  исправление), `interrupted → queued|cancelled` — по `/continue`; терминальные состояния
  только в архив, без возврата);
- дописывает в запись `transitions: [{ at, from, to, reason, actor }]` и `updatedAt`;
- недопустимый переход — ошибка с понятным текстом и запись в журнал сервиса, без молчаливой
  подмены статуса.

### Долговечная запись
`journal.save(record, { durable })`:
- обычная запись — как сейчас, сериализованный `appendFile` (используется для отметок
  прогресса `lastProgress`, которые не обязаны переживать сбой);
- принятие задачи И каждая смена состояния — `durable`: открыть файл на запись, записать
  строку, вызвать `fsync`, закрыть, дождаться результата. Так история переходов переживает
  сбой, и после перезапуска видно, где именно остановилась задача. Только после первой
  долговечной записи `submitBridgedTask` возвращает `taskId`, а мост — `202`.
- Компакция при старте — как сейчас: временный файл, `rename`, затем `fsync` каталога
  (переносимость `fsync` каталога проверяется в тесте и мягко деградирует на платформах,
  где он не поддерживается).

Ошибка записи (диск, права) не глотается: `save` бросает, вызывающий код решает, что
сказать. Для владельца — «задача не принята, повторите»; для моста — `503` без запуска.

### Очередь и восстановление
- `journal.openQueued(job)` создаёт запись `status: queued` с `order` (монотонный счётчик,
  инициализируется при загрузке как `max(order) + 1`) и всеми полями, нужными для запуска:
  `chatId`, `userId`, `text`/`request`, `attachments`, `route`, `requestKey`, `sessionId`,
  `scheduledFrom`, `retryOf`, `procedure` (PLA-16), `variantsMode`, `freshSession`.
- `journal.pending()` возвращает записи `queued` в порядке `order`.
- `AgentBot.start()` после `load()` и `compact()`:
  1. `recover()` в storage: `queued` — в очередь; `running` — `interrupted`;
     `awaiting_owner` — пересобрать `await:<chatId>` в `state.json` (если потерян);
  2. выставить в очередь только `queued`, в исходном порядке, затем запустить `drain`;
  3. один раз сообщить владельцу: сколько задач восстановлено и какие прерваны
     (без спама при рестарт-петле — через `startupNoticeAt`).
- `interrupted` сохраняет `lastProgress`: шаги, последний инструмент, время последней
  активности (обновляется из `onDshEvent` не чаще раза в 15 секунд) и список файлов
  рабочей папки новее `startedAt` (скан при восстановлении). Это и есть «доступные
  промежуточные результаты»; отчёт владельцу: задача прервана, файлы остались, `/continue`
  или `/retry`.
- Прерванная задача НЕ запускается автоматически: продолжение — только по решению
  владельца, потому что неизвестно, какие внешние действия успели произойти.

### Повторная постановка
- Ключ запроса `requestKey` (строка) хранится в записи; при загрузке строится
  `Map<requestKey, id>`; повторный `openQueued` с тем же ключом возвращает существующую
  запись с `duplicate: true` и не создаёт вторую.
- Для моста ключ — `requestId` из тела (обязателен для нового клиента, необязателен для
  старого); если ключ не передан, дедупликации нет, но это явно пишется в логе.
- Для задачи, пришедшей из группы моста в Telegram, ключ — `tg:<chatId>:<messageId>`:
  повторная доставка апдейта не создаст вторую задачу.
- Конфликт: тот же ключ с другим текстом задачи — ответ `409` и запись в лог, вторая задача
  не создаётся (лучше отказать, чем выполнить не то).

### Безопасное продолжение
- Новый журнал `src/storage/actions.mjs` (`actions.jsonl`, схема `version: 1`):
  `begin({ taskId, kind, target, key })` → `id`; `confirm(id, { receipt })`;
  `unknown(id, { reason })`; `unresolved(taskId)`.
- Внешнее действие (отправка файла, зеркалирование, позже — событие доставки) сначала
  пишется как `started` (долговечно), после успеха — `confirmed` с идентификатором
  подтверждения. Если процесс упал между `started` и `confirmed`, при восстановлении
  запись переводится в `unknown`.
- `/continue <id>`:
  - если у задачи есть `unresolved` действия — сначала спрашивает владельца, что именно
    произошло, и только после ответа продолжает; повтор внешнего действия без ответа
    запрещён;
  - продолжает с сохранённым `sessionId` (если есть), с пометкой в промпте: что уже сделано,
    что неизвестно, что делать дальше. Если сессии нет — новый запуск с тем же `id` и
    кратким описанием хода.
- `/retry <id>` остаётся прежним: новая задача с новым `id`, связь через `retryOf`.

### Конфиг
Новых обязательных ключей нет. Добавляются (со значениями по умолчанию):
`RECOVERY_NOTIFY` (true) — сообщать о восстановлении; `ACTION_LOG` (true) — вести журнал
внешних действий; `ACTION_LOG_MAX` (5000) — предел записей перед компакцией. Ключи
описываются в `config`, `.env.example` и README.

### Миграция и откат
- `TaskJournal.load` принимает `version: 1` и `2`; записи v1 переносятся в памяти, при
  первой записи получают v2. Старые строки не переписываются до компакции — история
  сохраняется.
- `state.json` продолжает хранить `await:<chatId>`; источник истины — журнал, состояние
  восстанавливается при старте.
- `actions.jsonl` создаётся пустым; для старых задач неизвестных действий нет.
- Откат: предыдущий релиз (симлинк). Предыдущий код пропустит строки v2 (схема новее),
  поэтому задачи, принятые после обновления, станут невидимы — откат выполняется только
  при остановленном приёме задач, с бэкапом `tasks.jsonl` и `actions.jsonl`.

## Влияние
- Меняются `src/storage/tasks.mjs`, появляется `src/storage/actions.mjs`, меняются
  `src/core/bot.mjs`, `src/bot-link/bridge-http.mjs`, `src/config/`, тесты и `.env.example`.
- Поведение владельца меняется только в сбоях: при нормальной работе те же сообщения, тот же
  порядок задач, те же команды; добавляется `/continue`.
- Риск: долговечная запись добавляет задержку на приём (один `fsync` на задачу) — измеряется
  тестом, порядок единиц миллисекунд; очередь остаётся одна.
- Риск: неверная миграция статусов ломает `/tasks`; закрывается тестом миграции на записях
  всех старых статусов.
- Откат: симлинк на предыдущий релиз + сохранить состояние (см. выше).

## Альтернативы
- Отдельный файл очереди (`queue.json`) рядом с `tasks.jsonl` — два источника истины и
  рассинхронизация при сбое; отвергнуто.
- Синхронная запись всей очереди в JSON на каждый шаг — дороже и рискованнее для истории
  (потеря старых записей при перезаписи); отвергнуто в пользу append-only + `fsync` только
  на границах (принятие, финальный статус).
- Автоматическое продолжение прерванных задач после рестарта — противоречит требованию
  «неизвестный исход действий нельзя повторять автоматически»; отвергнуто.
- Идемпотентность «по тексту задачи» — ложные совпадения у разных поручений; отвергнуто,
  ключ даёт клиент.
